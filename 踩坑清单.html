踩坑清单

本清单汇总编写与使用本课程过程中实际遇到过的两类问题：
第一类是学习 AI 应用技术本身会踩的坑；第二类是编写和维护这类教材时踩的坑。

两类分开列，因为修法完全不同：第一类靠理解机制，第二类靠检查机制。

第一类：技术本身的坑

这一类不靠「记住结论」解决，靠「知道为什么会这样」。

阶段 1 · Prompt 工程

现象 原因 规避方式
加了「不要编造」它照样编 只给了禁止项，没给替代动作 改成「资料未提及就回答『资料未提及』」——给它一个可执行的替代出口
每次输出字段名都不一样 没给完整结构示例 给出完整的输出样例（不是描述字段，是给一整条范例）
明明写了约束，模型还是没遵守 约束放在了提示词开头 最关键的约束放结尾——离生成位置最近，影响最直接
十条规则写下去，它还是不懂「礼貌」 规则本身不可判定 换成给三个例子——不可判定的标准用示例表达

阶段 2 · RAG

现象 原因 规避方式
用户问法与原文用词不同，就检索不到 纯关键词检索不认同义 混合检索（关键词 ＋ 向量），或对用户输入先做一次同义改写
改了文档，检索结果还是旧的 只改文件没重建索引 文档更新与索引重建必须绑定成一步
找到 20 段全塞进上下文，答案反而变差 噪音淹没了信号 限制 top-k（通常 3–5 段）
检索内容递过去了，模型还是自己编 没有给约束和替代动作 补「只依据给定资料回答」＋「资料未提及就明说」
以为微调能让模型「记住业务数据」 微调改风格与行为，不注入知识 要注入知识用 RAG；要改行为与格式才用微调

阶段 3 · Agent 与工具调用

现象 原因 规避方式
工具选错、参数填错 工具描述写的是「我是什么」而不是「什么时候该选我」 描述里写清适用条件 ＋ 给真实调用例子
模型反复调用同一个失败工具 工具失败后没给替代路径 错误信息要可执行（告诉它接下来能怎么做）
上下文越来越贵、越来越慢 轨迹只增不减 上下文压缩 ＋ 轮次上限
以为换更强的模型能解决「老是选错工具」 选错是描述问题，不是能力问题 先改工具描述，再考虑换模型
Agent 说做完了，其实没做完 「完成」只是一句宣称，不是证明 要执行结果、截图、测试这类独立证据

阶段 4 · 多 Agent

现象 原因 规避方式
多个 Agent 犯了同一个错 同质趋同——它们的「独立」是假的（同一模型、同一上下文） 有意引入差异：换模型、换上下文、换视角
A 把 B 的操作当成蓄意阻挠 目标互斥时从趋同变成对抗 预先定义目标优先级、资源所有权、权限边界
信息每转述一次就失真一次 转述链条越长失真越大 交叉验证：让某个 Agent 不看前序思考，只拿原始证据重新判断
活干到一半就停了，却报告「已完成」 过早终止：偷懒式假完成 / 过早放弃 / 悄悄换标准 用独立验证器核对，不看它的自我宣称
并发改同一个文件，逻辑互相矛盾 文件层不冲突，但语义冲突更隐蔽 用乐观锁；无法自动解决时暂停交人工

阶段 5 · 工程化

现象 原因 规避方式
以为开了 venv 就安全了 venv 只隔离包依赖，对文件系统、网络、进程没有任何约束 venv 管依赖，隔离要靠容器或 microVM
Dockerfile 里 ENV 写了真实密钥 ENV 会明文写进镜像层，docker history 直接能看到 密钥构建时用 -e 传参，或干脆不落文件
「先 COPY . . 再 rm 掉密钥文件」以为干净了 层不可变，删掉只是在上面加一层「标记它没了」 密钥只能从一开始就不 COPY 进去（.dockerignore 挡）
每次改代码都要重新构建很久 分层顺序错，缓存全废 依赖先装、代码后拷——依赖层不变就能复用缓存
以为「容器就是轻量虚拟机」 容器共享宿主机内核，虚拟机自带内核 按被绕过难度选隔离档：进程级 / 容器 / microVM
用 latest 基础镜像，今天和明天行为不一样 标签会漂 写死版本号
构建报 502 Bad Gateway 环境里注入了不通的代理地址 清空 HTTP_PROXY / HTTPS_PROXY / http_proxy / https_proxy / ALL_PROXY
拉镜像超时 IPv6 不通（IPv4 实测正常） 从国内镜像源预拉基础镜像
「改了之后好了一点」其实是随机波动 小幅度差异落在噪声范围内 重复评测 ＋ 配对分析，确认超出噪声才算改进
LLM 应用上线后变差却没人发现 最常见的退化是「不报错、但答得变差」 灰度期同时盯效果、错误率、延迟三项
改了提示词后想回滚，回不去 没记版本对应 模型版本 ＋ 提示词版本 ＋ 工具版本三者对应记录

阶段 6 · 垂直应用

现象 原因 规避方式
没有 API 就想上 Computer Use 跳过了判断顺序 第一步永远先问「这个系统有没有 API」——API 更快更稳可验证
流程很简单却上了框架 没走选型判断 流程简单、需求还在快速变时直接调 API
框架出问题时定位不到 每层抽象都是调试盲区 问一句：换个框架要改多少？改得多就是被绑住了
低代码平台搭的东西上线后没人管质量 业务方能自己改 ＝ 没人管变更 必须配版本记录 ＋ 变更评审

阶段 7 · 求职实战

现象 原因 规避方式
被要求写代码时慌了 没准备应对方式 先反问「这道题要验什么」——把话题从手速转到判断力
讲项目像流水账 只讲「做了什么」 重点讲 A 段：为什么这么选
回答和面试官的说法对不上 教材通行说法与自己学的说法同名不同义 主动桥接：「您说的四步是主循环，我这边拆得更细……」
搜「大模型岗位」全是 K8s 招聘量集中在 infra 岗 搜大模型应用 / LLM 应用 / Agent 开发 / RAG
把「资深要求」当「入行门槛」 招聘话术常把两者混写 「精通 X」＋「有大规模生产经验」是招资深，不是入门门槛

第二类：编写与维护教材的坑

这一类不靠理解，靠检查。每一条都对应一个可自动化的检查动作。

现象 原因 规避方式
答案泄露：选择题正确选项被加粗 为了批改时一眼看到答案，但同一份文件是给读者看的 写完必查：选项行是否以 ** 开头。加粗是给读者看的强调，不是给批改者的标记
HTML 内嵌判分键 为了离线能判分，把答案写进 JS 权衡取舍：内嵌则「查看源代码」可见
章节跳号：插入新节时把后面节号顶掉 手工改节号 改节号后必跑覆盖检查，看讲义节号与题库声明是否对齐
讲义与题库脱节：新补的内容没有对应题目 只顾加内容，没回头逐节对覆盖表 每改一次讲义，回头过一遍覆盖表
检查脚本假阴性：注入测试用例时锚点写错，注入失败却报「通过」 注入用的字符串和文件里的实际内容不一致 验证一个检查脚本，必须先证明它「能失败」；注入时加断言确认锚点存在
脱敏规则与检查模式不同源：检查报 N 处，处理脚本改 0 个 两边各写一套正则 两套模式必须同源，并在检查模式里加自检：能命中的样本，处理规则必须能消掉
正则删改把句子改坏 通配式删除吃掉了不该吃的部分 删完必须扫「破损句」：空括号、连续标点、残留加粗符号
标点后多空格 删除操作留下空格 收尾统一清理

这份清单怎么维护

技术类坑在讲义里就地标注（读者学到那儿就能看到），本清单是索引。
教材类坑是经验沉淀，新遇到就往上加——加的时候请写清「现象 / 原因 / 规避」三段，
只写「以后注意」没有用，因为下次会想不起来具体注意什么。

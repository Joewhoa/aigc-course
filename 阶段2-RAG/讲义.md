## 2.1 先回答前置问题：为什么不能把资料直接塞进提示词

回到阶段 0 学过的两件事：

- **Token 有上限**，这个上限叫上下文窗口
- 五问表里，**第 2 问是「塞得进上下文吗」**

所以：

> **RAG 存在的根本原因，就是「资料太多，塞不进上下文窗口」。**
> 不是为了让它更聪明，也不是为了省钱。

如果资料塞得进（几页以内），**直接用 Prompt，不要上 RAG**——这是上阶段刚踩过的坑。

**反过来说**：RAG 是「资料量超过窗口」时才会用到的重武器。
它有成本（要切块、要建索引、要维护、检索还可能出错），所以**能用 Prompt 解决就别上 RAG**。
这条判断在后面反复出现——2.6 讲用户记忆时会再撞一次。

## 2.2 RAG 的完整流程（五步）

这是本阶段最重要的一张图。

| 步 | 名称 | 干什么 | 一句话 |
|---|---|---|---|
| ① | **切块** | Chunking | 把长文档切成一段一段 |
| ② | **向量化** | Embedding | 把每段文字变成一串数字 |
| ③ | **入库** | Vector Store | 把这些数字存进一个能快速查找的地方 |
| ④ | **检索** | Retrieval | 把用户问题也变成数字，找出最接近的几段 |
| ⑤ | **生成** | Generation | 把找出的几段 + 用户问题一起发给模型 |

> 🧩 **想一想**：这五步里，哪一步是「离线做一次」的，哪一步是「每来一个问题都要做」的？
> （答案在本节末尾。）

### ① 切块（Chunking）

为什么不整篇塞？因为整篇太大——这就是 RAG 存在的理由。

怎么切？常见的三种：

| 方式 | 做法 | 适用 |
|---|---|---|
| 按段落切 | 一个自然段一块 | 结构清晰的文档（制度、手册） |
| 按固定长度切 | 每 500 字一块 | 结构不规整的文档 |
| 按语义切 | 用模型判断意思的边界 | 质量最高，成本也最高 |

**切块的核心矛盾**：

- 切**太大** → 检索出来的片段里一半是废话，浪费 token
- 切**太小** → 一句话被切断，意思不完整，模型看不懂

### ② 向量化（Embedding）

把一段文字变成**一串数字**（比如 1536 个数字）。

**关键特性：意思相近的文字，变成的数字也相近。**

这就是为什么能算「两段文字像不像」。它不靠字面重叠，靠意思。

### ③ 入库（Vector Store）

把这些数字存进一个地方。普通数据库也能存，但算相似度很慢；专门的向量库（或带向量索引的数据库）能**快速找出最接近的几条**。

这一步理解到「有个地方存着、能快速查」就够了，细节在阶段 5（工程化）再展开。

### ④ 检索（Retrieval）

用户提问 → 把问题也向量化 → 在库里找出最接近的 **top 3～5 段**。

**注意**：检索出来的不一定是「正确答案」，只是「向量上最接近的」。这一点在 2.4 会展开。

### ⑤ 生成（Generation）

把检索到的片段和用户问题拼成一段提示词，发给模型。大致长这样：

```
根据以下资料回答问题。

资料：
{检索到的第 1 段}
{检索到的第 2 段}
{检索到的第 3 段}

问题：{用户的问题}

只根据上面的资料回答。如果资料里没有相关内容，
直接回答「资料未提及」，不要自行推测。
```

> **最后那两句，就是阶段 1 学的「约束边界」写法。**
> RAG 的可靠性，一半靠检索，一半靠这段提示词。

### 五步串起来的一句话

> **RAG 没有让模型变聪明。它只是在提问的那一刻，把相关资料一起递给模型。**

### 补充：工业级流水线比这五步多两步

上面五步是**骨架**，够你理解和面试。但真实系统通常更长，完整版是：

> **分块 → 稠密/稀疏检索 → 融合 → 重排序 → 生成**

多出来的两步是：

| 多出的一步 | 干什么 | 对应我们学的 |
|---|---|---|
| **融合** | 同时用两路检索（关键词 + 语义），把两边结果合并 | 见下方「混合检索」 |
| **重排序** | 粗筛出一批之后，再用一个更精细的模型重新打分排序 | 2.4 节已讲 |

**「稠密 / 稀疏」分别是什么**：

| | 稀疏检索（Sparse） | 稠密检索（Dense） |
|---|---|---|
| 靠什么找 | **字面词重叠** | **语义相近** |
| 代表技术 | TF-IDF → **BM25** | Embedding + 向量库 |
| 强在哪 | 精确匹配专名、编号、代码 | 换个说法也能找到 |

**混合检索（Hybrid）**：两路都跑，结果合并。**这就是 2.4 节失效模式 1 的解法**——
关键词那路保证「字面一定不丢」，语义那路保证「换个说法也能找到」。

**你要记住的**：**面试说五步不算错**（那是骨架），但如果你能补一句
「工业级还会加混合检索和重排序」，面试官会知道你不是只看了入门文章。

### 🧩 回到刚才那个问题：哪几步是「离线」的

| 阶段 | 步骤 | 什么时候跑 | 为什么这么分重要 |
|---|---|---|---|
| **离线（建库时）** | ① 切块 ② 向量化 ③ 入库 | **建库时做一次**；文档变了重做 | 贵，但不用每次问都付 |
| **在线（每次提问）** | ④ 检索 ⑤ 生成 | **每来一个问题就跑一遍** | 直接决定响应速度和每次成本 |

**这条区分有实际用处**，尤其在阶段 7 面试里：

- 面试官问「**为什么你的回答慢**」→ 大概率卡在**在线**那两步：检索返回太多、或塞进去的资料太长。
- 面试官问「**知识库更新要多久才生效**」→ 那是**离线**那三步要重跑。**只更新文件不重建索引，新内容检索不到。**
  （这正是 2.8 要展开的问题。）

**一句话记法**：**离线建索引，在线查索引。** 出问题先判断自己卡在哪一边。

## 2.3 向量化 vs 更经典的 TF-IDF

TF-IDF 和 Embedding 是**同一类东西**，但有一个关键差别：

| | TF-IDF | 向量化（Embedding） |
|---|---|---|
| **靠什么算相似** | **字面词重叠**（出现同样的词） | **意思**（模型学出来的语义） |
| 例：「报销被拒」vs「报账没通过」 | 词不一样 → 相似度低 | 意思一样 → 相似度高 |
| 优点 | 简单、快、不需要调模型 | 能理解同义、换个说法也能找到 |
| 缺点 | 换个说法就找不到 | 要调模型、慢一些、贵一些 |

### 账单类场景为什么用 TF-IDF 就够了

**因为账单里的关键信息本来就是字面匹配的**——商户名、金额、日期、订单号，这些不需要「理解意思」。

用 TF-IDF 又快又准又省。**这是「按场景选工具」，不是「用了过时的技术」。**

反过来，如果要做一个「员工手册问答」，用户会用各种说法问同一件事——那时候 TF-IDF 就不够了，得上 Embedding。

### 你可能有的一个直觉，先纠正掉

很多人第一次听「向量」会想：**这不就是 Python 里的数组（列表）吗？**

**一半对。** 形式确实像——都是一串、能按下标取第几个、能算加减。

**但关键差别在这里**：

| | Python 的列表 | 向量（Embedding） |
|---|---|---|
| 里面装的是 | 什么都能装（数字、文字、对象） | **只能是数字**（几百到几千个） |
| 有意义吗 | 每一项都是独立的东西 | **每个数字单独看没意义，整串一起才有意义** |
| 怎么用 | 遍历、取值、排序 | **算两串之间的「距离」** |

**「距离」是什么意思**：把两串数字当成空间里的一个点，算它们的远近。
**两点越近 = 两段文字意思越像。**

比如「报销被拒」和「报账没通过」会被变成两个靠得很近的点，而「报销被拒」和「今天天气不错」离得很远。

> **所以别把它当数组去理解每一项的含义。** 它是一整串一起表达「这段话在说什么」。
> 就像指纹——你不会去问「指纹第 3 条纹代表什么」，只看整体像不像。

## 2.4 RAG 会在哪里出错（四种失效模式）

这一段面试最爱问。

| # | 失效模式 | 表现 | 根因 | 怎么防 |
|---|---|---|---|---|
| 1 | **检索没找到** | 资料里明明有，它说没有 | 切块把关键信息切断了；用户用词和原文差太远 | 调整切块策略；混合检索（关键词 + 向量一起用） |
| 2 | **检索错了** | 找到的是不相关的段落 | 相似度算法把「字面像但意思不同」的排到了前面 | 加一层重排序（rerank）；加过滤条件（按时间、按类别） |
| 3 | **找到了但不看** | 资料递过去了，它还是自己编 | 提示词里没要求「只根据资料回答」 | 阶段 1 的约束写法：只依据资料 + 资料未提及就明说 |
| 4 | **找到太多** | 塞了 20 段进去，噪音淹没了有效信息 | 没有限制检索数量 | 限制 top-k（一般 3～5 段）；把最相关的排前面 |

### 第 3 条最容易被忽略

很多人以为「把资料给模型，它就会用资料」。**不会。**

不明确要求，它照样会掺自己的记忆进去——这跟阶段 1 讲幻觉时是同一个道理：
**只禁止不给替代动作，等于没约束。**

所以 RAG 的提示词里必须写：

> 只根据上面的资料回答；资料里没有的，直接回答「资料未提及」。

### 顺带说清：过滤（filter）与重排序（rerank）

这两个词在失效模式 1、2 里出现，展开一下：

| 手段 | 在流程的哪一步 | 干什么 |
|---|---|---|
| **过滤（filter）** | 检索**之前** | 先按字段圈定范围，比如「只查 2024 年以后的」「只查财务类目」——把不相关的直接排除在检索池外 |
| **重排序（rerank）** | 检索**之后** | 先用向量粗筛出 20～50 条，再用一个专门的重排模型逐条打分，取分数最高的前 3～5 条 |

**区别一句话**：过滤是「先把范围缩小」，重排序是「把粗筛结果重新精排」。

## 2.5 一条必须记住的边界：RAG 不解决「算得准」

RAG 解决的是「**知不知道**」，不解决「**算得对不对**」。

以账单核对为例：

| 环节 | RAG 能做吗 |
|---|---|
| 从一堆账单里找出相关的那几条 | ✅ 这是检索 |
| 判断两条账单的金额加起来是否相等 | ❌ **必须用代码算** |

**这是阶段 0 五问表第 1 问的复用**：必须精确算出来的东西，交给代码，不交给模型。

### 那「算」这件事该谁干

| 活儿 | 谁干 | 为什么 |
|---|---|---|
| 找出相关的那几条账单 | **检索**（RAG 的活） | 靠相似度，允许模糊 |
| 把两条金额加起来比大小 | **代码**（Python / SQL） | 要 100% 确定，一个字都不能错 |
| 判断「这笔支出算不算差旅」 | **模型** | 有模糊空间，靠语义判断 |

**看出规律了吗**：

> **答案是「确定的」，交给代码；答案是「模糊的」，交给模型。**
> **RAG 只负责把模型需要的那几段资料递过去，不改变这条分工。**

所以「账单核对项目」这类系统真实的做法是：**RAG 负责找依据 → 代码负责算数 → 模型负责把结果说成人话**。
面试里能主动说出这条边界，是明显的加分项。

## 2.6 「用户记忆」和「知识库」不是一回事（★ 重要区分）

前面五节讲的全是**知识库**。但面试官问「Agent 怎么做记忆」时，
**只答 RAG 是答偏了**——因为「记忆」和「知识库」是两个东西。

### 一句话说清区别

> **知识库是「对所有人一样的公共知识」；用户记忆是「每个人不同的私人信息」。**

书里的原话：「知识库为整个组织提供共享的统一知识，而用户记忆则为每个用户维护私人信息。
**这两个尺度有本质区别：知识库关注群体的公共知识，用户记忆关注个体差异。**」

| | 知识库（RAG） | 用户记忆 |
|---|---|---|
| 服务对象 | **所有人一样** | **每个人不同** |
| 例子 | 产品手册、公司制度、FAQ | 这个用户偏好简短回答、他是财务岗 |
| 谁维护 | 组织统一维护 | 系统**自动从对话里提取** |
| 更新频率 | 文档变了才更新 | 每次交互都可能更新 |
| 失效后果 | 答错事实 | **把别人的信息给了你**（隐私事故） |

### 记忆其实有三层（别只想到「跨会话」）

| 层 | 是什么 | 生命周期 |
|---|---|---|
| **轨迹** | 单次任务的完整消息历史（阶段 3 讲过） | **一次任务** |
| **用户长期记忆** | 跨会话稳定的用户信息 | **长期** |
| **业务状态** | 高层任务的阶段进展 | **任务周期** |

**这里有个容易混的点**：轨迹是**不可变的原始记录**，工作记忆是它的**动态子集**。
好比：会议录像是轨迹，会议纪要摘要是工作记忆——录像是不能改的，摘要是随时更新的。

### 记忆怎么存：四种格式，按「重要性 × 数量」选

| 格式 | 长什么样 | 适合什么 |
|---|---|---|
| **简单笔记** | 纯文本一行一条 | **量大但不关键**（浏览记录） |
| **增强笔记** | 带标题/日期的 Markdown | 中等结构需求 |
| **JSON 卡片** | 固定字段的结构化数据 | **关键、量少** |
| **高级 JSON 卡片** | 支持多值、高亮、信息级别 | **关键且要精确**（比如病史、过敏史） |

**选择标准**：**关键且量少**（病史、过敏史）→ 用高级 JSON 卡片；
**量大且非关键**（浏览记录）→ 用简单笔记。
**多数生产系统是混合用的**，不是只用一种。

### ⚠️ 一个反直觉的结论（这条最能体现你懂不懂）

**用户记忆通常不需要向量库。**

**为什么**：记忆条目通常只有几十到几百条——
**这个量级，全部直接塞进上下文比搭一套检索更简单、更准、更省。**

**看出这是什么了吗——这就是阶段 0 的「五问表第 2 问」：塞得进就直接给，别上 RAG。**
**同一个铁律，换了个场景又用上了。**

### 记忆写入的三条规则（这部分是「怎么做」）

从对话里存记忆，是**用额外的一次模型调用**做提取和压缩。三条规则：

| 规则 | 意思 |
|---|---|
| **选择性** | 不是每句话都值得记。判断「这条信息将来有用吗」 |
| **抽象化** | 原话可能是「我今天在深圳」，记下来应该是「常住深圳」 |
| **结构化** | 存成机器能用的格式，不是流水账 |

**注意「额外一次调用」这件事**：记忆是有成本的。所以**不是记得越多越好**——
记太多反而会占用上下文、引入噪音。

## 2.7 Agentic RAG：把「检索」变成「工具」

前面讲的 RAG 是一条**固定的管道**：不管什么问题，都走一遍
「切块 → 检索 → 重排序 → 生成」。

**问题是**：有些问题一遍检索就够了，有些问题需要**边查边想、查好几轮**。

### 区别在哪

| | 传统 RAG | **Agentic RAG** |
|---|---|---|
| 检索次数 | **固定一次** | **Agent 自己决定几次** |
| 谁在主导 | 流程代码 | **Agent 的 ReAct 循环** |
| 检索是什么 | 管道里的一个环节 | **Agent 手里的一件工具** |
| 适合 | 问题直接、一次能查全 | 需要多跳、要先判断「查到够不够」 |

### 它怎么工作

**就是把「检索」变成阶段 3 的工具，然后交给 ReAct 循环**：

```
想：这个问题需要先查什么？
做：调用「知识库检索」工具
看：返回的这三段够回答吗？还有哪块缺？
想：缺的那块要换个关键词再查
做：再调一次检索
看：够了
→ 生成答案
```

**看出来了吗——它不需要新机制，就是把阶段 3 的循环用在了检索上。**

### 什么时候用

| 用 Agentic RAG | 用普通 RAG |
|---|---|
| 问题需要**多跳推理**（A 的答案要先去查 B） | 问题直接，一段资料就能答 |
| 检索质量**不确定**，需要 Agent 判断「够不够」 | 检索质量稳定 |
| **成本不敏感** | 成本敏感（多轮检索 = 多次模型调用） |

**⚠️ 别一上来就上 Agentic RAG**：它比普通 RAG **贵**（多几轮调用）、**慢**。
又是同一条铁律——**能用简单方案就别上复杂的。**

## 2.8 知识怎么更新（★  按教材补）

前面七节讲的是「**怎么建**」一个知识库。但建好只是开始——**真实的知识库会一直收到新信息。**

书的原话：

> 「只更新不整理，内容会越积越乱；只做定期重写，新信息又无法及时生效。
> 因此，完整的更新机制必须同时包含两条路径：**事件触发的增量更新**，以及**周期触发的全量整理**。」

（出自李博杰《深入理解 AI Agent》第 3 章「知识应该如何更新」）

### 两条路径，缺一不可

| 路径 | 什么时候跑 | 解决什么 |
|---|---|---|
| **增量更新** | 一有新信息就触发 | **及时**——新政策当天生效 |
| **全量整理** | 周期性（每周 / 每月）或超过阈值时 | **不乱**——防前后矛盾、重复、碎片化 |

> ⚠️ **别忘掉 2.2 那个「离线 / 在线」区分**：
> 「文件更新了」≠「检索到新内容了」。
> **改完文件必须回到离线那三步：重新切块 → 重新向量化 → 重建索引。**
> 只改文件不重建索引，是新手最常踩、也最容易被面试官逮住的一个坑。

### 增量更新：把知识库当代码库

书里给的最稳妥答案是：

> 「**把知识库当成代码库，把每次知识变更当成一个 Pull Request（PR）**。」

四步（**提议者—审核者**模式）：

| 步 | 谁干 | 干什么 |
|:--:|---|---|
| 1 | **提议者** | 从新证据里发现新事实 / 冲突 / 过期内容 → **在工作分支上提一个尽量小而完整的改动**（**不是**把新对话直接追加到文件末尾） |
| 2 | **审核者** | **独立**核对：每个新说法**有没有证据支持**？漏了限定条件吗？跟别的文件冲突吗？ |
| 3 | 迭代 | 提议者按意见改，审核者回到**原始证据**复核；**只有审核者明确批准才能合入** |
| 4 | 合入后 | 先跑检查，通过后**增量重建受影响的分块与索引** |

**⚠️ 四个硬要求**（书里点名）：

- **提议者和审核者必须是 Agent，不是两次固定调用**——它们得能自己去搜、去比、去跑检查
- **两个 Agent 用不同家族的模型**（如 DeepSeek + Kimi）→ 降低「在同一处犯同类错」的概率
- **权限强制分工**：提议者只能写工作分支，审核者只读证据、只提审核结果，**只有合并流程能改主分支**
- **绝不能绕过审核直接改线上向量库**

### ⭐ 一句话记住整个设计

> **索引是可重建的「派生物」；Git 里已审核的知识，才是真正的来源。**

所以书里要求**分三层**：

| 层 | 存什么 | 规则 |
|---|---|---|
| **原始证据层** | 对话、轨迹、原始文档 | **只增不改** |
| **知识层** | 提炼后的 Markdown / 代码 | **可修订，走 PR** |
| **服务层** | 检索用的索引 | **从某个已合入的版本重建** |

**为什么重要**：如果一开始就把「模型提炼的摘要」当唯一真相，**早期的误读会一代代传下去**。
保留原始证据，才能**随时回到源头核对**。

### 定期整理：干三件事

1. **去重、去旧、合并** —— 删 / 并 / 重写语义重复、已被取代、过度碎片化的条目；重建索引页
2. **回到原始数据核查** —— **不能只在旧摘要之间互相改写**；要逐段对照原始对话与文档，
   检查有没有**漏掉否定词或时间条件**、有没有**把推测当成事实**
3. **冲突不强行收敛** —— 两条矛盾记录，先追溯各自的原始来源，看是不是**在不同时间 / 对象 / 条件下都成立**；
   是就**把适用条件写进知识**，不是就保留「待确认」。**禁止硬猜哪个对**

### 失效内容必须下线（这条最容易漏）

> 一篇被新版取代的旧政策若还在库里，检索时可能**和新版一起被召回**，
> 让模型给出**自相矛盾、甚至过时**的答案。

标准做法：给每一块附**版本号 + 生效 / 失效时间**，**在检索阶段就过滤掉已失效的**。

### 多用户共享：权限必须在检索层过滤

> 「所有用户」≠「所有内容对所有人可见」。

**检索必须按调用者的权限过滤**——一旦敏感内容进了模型的上下文，就很难保证它不泄露到回答里。
多租户还要保证**各租户的向量索引互相隔离**，避免「串味」。

### ⭐ 重建期间，线上服务不能停

前面说了「改文件必须重建索引」。但这里有个**现实问题**没人提：

> **重建索引要跑 40 分钟。这 40 分钟里，用户还能不能问？**

**不能停。** 停 40 分钟做维护，业务上是不可接受的。所以标准做法是**换着用**：

| 做法 | 怎么做 | 大白话 |
|---|---|---|
| **双索引切换**（最常用） | 线上照旧用**旧索引**；同时在旁边用**新文档**建**一套新索引**；建完**一次性切换**过去，旧的那套下线 | **换灯泡不停电**——先把新的装好，再一键换 |
| **增量 + 定期全量** | 新政策走增量（只重建受影响的那一小块，秒级 / 分钟级）；季度大整理才做全量重建 | 小事随手改，大扫除安排在闲时 |
| **定时窗口** | 全量重建安排在凌晨等低峰期 | 关店后装修 |

**说清这条的分量**：面试官问「索引重建要多久、期间怎么办」时，
答「重建要 40 分钟，所以不可能停机做」**比只答「重建索引」高一档**——
前者说明你**考虑过线上可用性**，后者只是背了流程。

**收口句**：**索引是可重建的派生物，所以可以让新旧两套同时存在**——
这正是「索引不是真相、只是个能随时重做的副本」这条原则带来的好处。

#### 更准的一层说法：索引是「指向」

上面那句还停留在讲**索引的性质**。深一层要问：**为什么它可以随便重做？**

因为——**真相是"已审核入库的那份数据"，索引只是"指向它的一个指针"。**

| | 是什么 | 能不能丢 |
|---|---|---|
| **已审核的数据** | **真相来源**（唯一的那一份） | ❌ 不能丢——它是本体 |
| **索引** | 指向这份数据的**加速通道** | ✅ 随便丢，重做一次就回来 |

**这一层带来的两个直接结论**：

1. **两套索引可以并存** —— 它们都只是**指向同一份真相**，不存在「谁更新谁更对」的问题。这就是双索引切换能成立的全部理由。
2. **旧索引作废不会丢东西** —— 丢掉的只是"一条指向新数据的路"，数据本身还在原地。

> **面试可以这么说**（比只说「索引是可重建的派生物」更扎实）：
> 「**真相是那份已审核的数据，索引只是指向它的指针——指针可以同时存在两条，换一条不影响数据本身。**」

### 面试怎么用

被问「**手册每季度更新，你怎么保证答案不过时**」，按这个顺序答：

1. **两条路径**：新政策进来走增量更新（当天生效）；每季度走一次全量整理
2. **变更走审核**：提议者提 PR → 审核者独立核证据 → 批准才合入 → 合入后才重建索引
3. **旧版要下线**：每块打生效 / 失效时间，检索时过滤掉失效的
4. **重建不停服务**：新旧两套索引并存、建完切换（追赶者问「重建期间怎么办」时的答案）
5. **收口句**：**索引是可重建的派生物，已审核的知识才是真相来源**

## 2.9 微调：它到底在改什么（⚠️ 最常见的误解就在这一节）

**先说结论**：**微调不是「往模型脑子里塞知识」。** 这是这个领域最普遍、也最贵的误解——
**塞了知识却用了微调，等于花了十倍的钱，得到一个会过期的答案库。**

### 微调改的是「行为」，不是「知识」

| | 改的是什么 | 打个比方 |
|---|---|---|
| **RAG** | 给模型**一份可以随时换的手册** | 上班前发一本最新规章手册 |
| **微调** | 改模型**长期的行为习惯** | 让它去上个岗培训，学成某种岗位的说话与做事方式 |

**关键区别在「可更新性」**：

- **RAG 的知识可以随时替换** —— 手册改一页，明天就是新的
- **微调的行为改一次就是固定的** —— 要改行为，**得重新训练一遍**

### 所以什么时候该用哪个

| 你的需求 | 该用 | 为什么 |
|---|---|---|
| 「答案必须反映最新制度」 | **RAG** | 内容会变，微调追不上 |
| 「答案必须引用具体条款原文」 | **RAG** | 微调学不出原文，会编 |
| 「输出格式必须绝对稳定」 | **微调** | 格式是行为问题，不是知识问题 |
| 「语气必须符合品牌规范」 | **微调** | 语气是长期行为，RAG 做不到 |
| 「业务量极大且格式已固定」 | **微调**（可省大量 token） | 稳定的模式走微调更省成本 |

### ⚠️ 三种典型误用

| ❌ 常见误用 | 为什么不成立 |
|---|---|
| 「我们有 800 页产品手册，用微调让它记住」 | **微调学不进 800 页文档的细节**，它会记住大概的「感觉」，检索具体条款时照样编 |
| 「数据每次都变，所以每次变更都微调一次」 | **训练成本远高于重建索引**，且知识更新还得等重训完 |
| 「微调 = RAG 的进阶版，效果更好」 | **两者解决不同问题**，不存在替代关系 |

> **一句话记住**：**要用会变的东西，用 RAG；要改稳定的东西，用微调。**

### 面试怎么讲这一段

> 「**微调和 RAG 不是替代关系**——RAG 给的是**可随时替换的知识**，
> 微调改的是**长期的行为模式**。所以要**内容会变、要求引用原文**的场景，我用 RAG；
> 要**格式绝对稳定、语气统一**的场景，我才考虑微调。
> **把微调当知识库用，是这个领域最贵的一个误解**——它学不进具体内容，
> 而且内容一变就得重新训练。」

## 2.10 面试会怎么问

| 面试官问 | 别这么答 | 该这么答 |
|---|---|---|
| 「什么是 RAG？」 | 「就是给 AI 加个知识库」 | 说**五步**：切块 → 向量化 → 入库 → 检索 → 生成；可补一句工业级还有**混合检索 + 重排序** |
| 「**Agent 怎么做记忆**？」 | 「用 RAG」 | ⭐ 先区分：**知识库是群体公共知识，用户记忆是个体差异**；再说记忆的三层 |
| 「**Agentic RAG 是什么**？」 | 「更高级的 RAG」 | 把**检索变成 Agent 的一个工具**，交给 ReAct 循环，自己决定搜几次 |
| 「**你的 RAG 回答为什么这么慢**？」 | 「模型慢」 | 先分**离线 / 在线**：建索引是离线的、不影响每次响应；**慢只可能慢在在线那两步**——检索返回太多（收窄 top-k）、或塞进上下文的资料太长 |
| 「**知识库更新了，多久能生效**？」 | 「存进去就生效了」 | ⚠️ **改文件 ≠ 生效**——必须**重跑离线三步**（重新切块 / 向量化 / 重建索引），否则检索不到新内容 |
| 「**手册每季度更新，怎么保证答案不过时**？」 | 「定期重建索引就行」 | **两条路径**：增量更新（新政策当天生效）＋ 全量整理；**变更走 PR 审核**（提议者 / 审核者异源互审）；旧版打**失效时间**在检索层过滤；**重建不停服务**（双索引建完再切换）；收口：**索引是可重建的派生物，已审核的知识才是真相来源** |
| 「**索引重建期间服务怎么办**？」 | 「挑半夜重建」 | **双索引切换**——线上照旧用旧索引，旁边用新文档建新索引，建完一次性切过去。**能答出这条说明你考虑过线上可用性** |
| 「RAG 和微调什么区别？」 | 「RAG 便宜，微调贵」 | RAG 给的是**知识**（外挂手册）；微调改的是**风格**（说话习惯） |
| 「RAG 效果不好怎么排查？」 | 「换个更好的模型」 | 按**四种失效模式**逐个定位，先分清是「没找到」还是「找到了不用」 |
| 「怎么保证 RAG 不瞎编？」 | 「用更准的向量模型」 | 提示词里约束「只依据资料 + 资料未提及就明说」；要求它标注引用出处 |
| 「文档怎么切块？」 | 「切成 500 字一块」 | 说清 **trade-off**：太大浪费 token、太小切断语义 |

## 本阶段要带走的五句话

1. **RAG 的存在理由只有一个：资料塞不进上下文窗口。** 塞得进就用 Prompt。
   （**用户记忆也是这样**——几十条记忆直接塞上下文，不用向量库。）
2. **五步流程：切块 → 向量化 → 入库 → 检索 → 生成。** RAG 不会让模型变聪明，它只是把资料递过去。
3. **五步分成两半：离线三步建索引，在线两步查索引。** 排查问题先判断卡在哪一边。
4. **RAG 解决「知不知道」，不解决「算得对不对」。**
   确定的答案交给代码，模糊的答案交给模型。
5. **「用户记忆」和「知识库」是两个东西。** 前者管个体差异，后者管群体公共知识。
   面试问「Agent 怎么做记忆」，只答 RAG 是答偏的。

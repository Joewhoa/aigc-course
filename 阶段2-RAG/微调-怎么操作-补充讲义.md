## 1. 先建立一个直觉：微调到底动了什么？

### 常见误解：以为微调是「往模型里塞资料」

大部分人第一反应是这样想的：

> 「我要模型懂我的业务 → 那我就把业务资料喂给它 → 它就懂了」

**这个理解是错的**，而且错得很关键。

**准确的比喻**：

| | 类比 | 动的是什么 |
|---|---|---|
| **RAG** | 给一个人**桌上放一本手册**，他答题时随时翻 | 手册（**外部资料**），人不变 |
| **微调** | 让一个人**反复练习一种说话方式**，练成了肌肉记忆 | 人（**模型内部的参数**），手册不变 |

**关键差别**：
- RAG 改的是「**它手边有什么**」
- 微调改的是「**它习惯怎么反应**」

### 微调真正改变的是什么？

模型内部有**几十亿到几千亿个数字**（叫「参数」或「权重」），这些数字决定了它怎么说话。

**微调 = 拿你自己的例子，把这些数字稍微调一调。**

调的方向不是「记住内容」，而是「**对齐你想要的反应方式**」。比如：

| 你喂的例子 | 模型学会的「反应方式」 |
|---|---|
| 1000 条「用户问 X，我们客服这样回」 | 学会你们客服的**语气、话术、格式** |
| 500 条「把这段文字变成 JSON」 | 学会**稳定输出 JSON 格式**（不跑偏） |
| 300 条「复杂问题，只答一句结论」 | 学会**简短作答的行为习惯** |

⚠️ **注意「行为习惯」这四个字**——微调学到的是倾向，不是硬规则，也不是知识库。

## 2. 具体怎么操作？用你的项目走一遍

假设明天你要做一个场景：**账单助手的回答要严格符合公司的固定格式**（先给结论、再给依据、最后给金额）。

现在的做法是每次都在提示词里写「请按以下格式回答……」，**但模型有时会跑偏**。

**微调的完整流程（六步）：**

### 第 1 步：准备数据（这是最花时间的一步，占 70% 工作量）

你要做的是：**手工整理几十到几千条「问题 → 标准答案」的例子。**

```
输入：这笔订单的金额对得上吗？
输出：结论：对不上。
      依据：订单 A（¥1,200）＋ 订单 B（¥800）＝ ¥2,000，
            账单记录为 ¥2,100，差额 ¥100。
      金额：差额 ¥100。
```

**关键点**：
- 例子**不用多**，几百条好的例子就够（远少于模型的全部知识）
- 例子的**质量比数量重要**——要的是「标准答案」，不是随便写的答案
- 必须**覆盖你想要的各种情况**（包括「查不到资料」这种边界情况）

### 第 2 步：写系统提示词 + 选基础模型

- **系统提示词**：总规则（比如「你是账单助手」）
- **基础模型**：你要改哪个模型？可以是通用大模型，也可以选一个小模型来省钱

### 第 3 步：开始训练

把数据喂进去，机器开始调那些数字。**这一步你不用管细节**，只要：

- 选「训练轮数」（epoch，就是把这些例子过几遍，通常 3-5 遍）
- 选「学习率」（learning rate，每次调整的幅度，太大练歪、太小练不动）
- 等

**时间开销**：小模型几十分钟，大模型几小时到几天。

### 第 4 步：评测（⚠️ 这一步最容易偷懒，也最重要）

**不能只看训练时的分数**——那会骗人（模型把例子背下来了，但没学会）。要**留一批没喂过的例子**来测。

测试要看两件事：
1. **格式对不对**（要 JSON 就得是合法 JSON）
2. **内容有没有变差**（微调之后它会不会别的能力退化了？这叫「**灾难性遗忘**」）

### 第 5 步：部署使用

训练完会产出一个「**新的模型文件**」。你把它换上去，之后所有请求都走这个模型。

⚠️ **关键区别在这里**：RAG 更新知识是「**换个文件**」；微调更新知识是「**重新训练一遍**」。

### 第 6 步：维护

| | RAG | 微调 |
|---|---|---|
| 知识更新成本 | 换文件（分钟级） | **重新准备数据 + 重新训练**（天级） |
| 数据泄露风险 | 低（资料在外） | ⚠️ 训练数据进了模型内部 |
| 排查问题 | 能追到「用了哪段资料」 | ❌ **不可解释**，只能看输出对不对 |

## 3. 三个必须分清的词：SFT / LoRA / RLHF

面试听到这三个词不要慌，它们是在回答「**微调的具体方式**」这个问题。

### SFT（Supervised Fine-Tuning，监督微调）

**是什么**：最常见的一种微调。就是拿「问题 → 标准答案」成对的例子去训练。

**大白话**：**照着标准答案练**。给它看题目和答案，让它模仿。

**什么时候用**：想让它学会一种固定的回答格式、语气、做事流程。**90% 的业务场景做到这一步就够了。**

### LoRA（Low-Rank Adaptation，低秩适配）

**是什么**：一种**省钱的微调技术**。不去动模型里那几十亿个数字，而是**在旁边挂一小块东西**，只训练这一小块。

**大白话**：**不重装修，只挂个帘子**。原来的房子（大模型）一动不动，只加一点你自己的东西。

**好处**：
- 便宜很多（训练成本可能是全量微调的几十分之一）
- **快**（几小时 vs 几天）
- **可以换**：一个基础模型可以挂好几个不同的「帘子」，按场景切换

**⚠️ 面试要点**：现在说「微调」，工业界**默认指的是 LoRA 这种**，不是从头改整个模型。能说出这一点，面试官会知道你接触过真实工程。

### RLHF（Reinforcement Learning from Human Feedback，人类反馈强化学习）

**是什么**：更进阶的一种。不是给标准答案，而是给「**哪个回答更好**」的偏好判断，让模型自己摸索。

**大白话**：**不告诉它标准答案，只告诉它「这个比那个好」**，让它自己去试。

**什么时候用**：让模型更「符合人类喜好」（更有用、更无害、更诚实）。

**⚠️ 你的层级**：**知道它存在、知道它和 SFT 的区别就够**。你不用会做 RLHF——那是模型公司干的活。

## 4. 一张表把概念钉死

| 问题 | RAG | 微调 |
|---|---|---|
| **改什么** | 手边有什么资料 | 模型习惯怎么反应 |
| **怎么改** | 换文件、重建索引 | 拿例子重新训练 |
| **成本** | 低（分钟级） | **高（天级 + 算力钱）** |
| **适合放什么** | 业务知识、会变的资料 | 格式要求、语气、固定流程 |
| **更新方式** | 换文件即可 | **重新训练** |
| **能不能查到依据** | ✅ 能（用了哪段资料） | ❌ 不能（黑箱） |
| **数据安全** | 资料留在外部 | ⚠️ 数据进模型内部 |
| **最主流的真实用法** | 业务问答、客服知识库 | **用小模型替代大模型来省钱** |

### ⭐ 最主流的工业用法，你上一轮漏了这条

公司为什么微调？**很多时候不是为了调风格，是为了省钱。**

> 用大模型（贵）跑通一个场景 → 收集几千条「大模型的好回答」→
> **拿这些数据微调一个小模型** → 小模型干同样的活，**成本降到几十分之一**。

这个用法叫「**蒸馏**」（让小的学大的）。**面试提这个，比只答「调风格」显得懂行情。**

## 4·补、「小模型」到底是什么？（2026-09-23 他提问后补）

⚠️ **先说一个我上一版用词不清的地方**：

我在两个不同的意思上用了「小模型」这个词，**它们不是一回事**：

| 我说的场合 | 「小模型」指什么 | 大白话 |
|---|---|---|
| 「可以**选一个小模型**来微调」 | **同一个模型的轻量版**（厂商通常同时提供大杯和小杯，比如同一个系列有「标准版」和「轻量版」） | **同一道菜的小份**——配方一样，量少、便宜、快 |
| 「用它替代大模型来省钱」 | **一个本身就比你原来用的模型更小、更便宜的模型** | **换一家更便宜的馆子**——菜谱不同，但做出来够用 |

**但这两件事指向同一个目的**：**花更少的钱，干一样的活。**

### 那「训练小模型」的过程是什么？

**核心原理一句话**：

> **大模型当老师，小模型当学生。学生照着老师的样子练，练到够用为止。**

（这就是「蒸馏」这个词的由来——**把大的那一身本事，蒸馏到小的身上**。）

**具体四步**：

| 步 | 做什么 | 大白话 |
|:--:|---|---|
| ① | **先让大模型干活** | 拿它跑你这个场景（比如账单问答），跑出几千条回答 |
| ② | **人工挑出好的** | 大模型的回答不是每条都好，**挑出对的那批当教材** |
| ③ | **拿这批教材训练小模型** | 就是我们前面讲的微调流程——**小模型照着学** |
| ④ | **上线小模型** | 之后所有请求走小模型，**大模型只在「出教材」时用** |

### ⭐ 为什么这样能省钱（算给你看）

这是整件事的关键，也是面试的得分点：

| | 大模型 | 微调后的小模型 |
|---|---|---|
| **单次调用成本** | 贵（假设 1 块钱一次） | **便宜（假设 3 分钱一次）** |
| **谁付钱** | **每一次用户提问都付** | **每一次用户提问都付** |
| **训练成本** | —— | 一次性（比如几千块） |

**关键在「次数」**：

> **调用量大到一定程度，训练那笔钱会被摊薄到可以忽略。**

举个例子（数字是假设的，方便看比例）：

- 每天 10 万次调用 × 大模型 1 元 = **每天 10 万元**
- 每天 10 万次调用 × 小模型 0.03 元 = **每天 3 千元**
- 训练小模型一次性花 5 万 → **不到两天就赚回来了**

**所以这句话要记住**：

> **小模型不是「免费的便宜货」，是「用一次性的训练成本，换长期的调用成本下降」。**
> **调用量越大越划算；调用量小的时候，反而不划算。**

### 面试怎么答这块

被问「微调能省钱吗，怎么省」，按这个说：

> 「最主流的用法是**蒸馏**——先用大模型跑通场景，
> 把它的好回答收集起来当教材，再拿这些数据微调一个小模型，
> 之后线上就走小模型。
>
> 省的是**调用**的钱——大模型每次提问都贵，小模型便宜很多，
> 而且调用量越大越划算，因为训练那笔一次性成本会被摊薄。
>
> 所以这不是「小模型一定便宜」，而是**「调用量足够大的时候，用一次性训练换掉长期调用成本」**。」

⚠️ **别说成「用小模型就不用花钱了」**——训练要钱、要数据、要评测，
它是**换一种花钱的方式**，不是不花钱。

### ⚠️ 代价：不是白省的

| 代价 | 说明 |
|---|---|
| **能力会降** | 小模型在很多任务上**确实不如大模型**，挑对场景（任务单一、格式固定）才划算 |
| **要有人挑数据** | 「哪些是老师的好回答」得人来判断，**这是主要工作量** |
| **要重训** | 需求变了、老师升级了，蒸馏出来的小模型可能要重做 |
| **评测不能省** | 必须证明「小模型在**这个场景**上够用」，不是「差不多就行」 |

## 5. 什么时候**不该**用微调（面试分水岭）

| 场景 | 该用 | 为什么 |
|---|---|---|
| 回答业务知识、内部文档 | **RAG** | 知识会变，微调一次就过期 |
| 资料要能查到出处 | **RAG** | 微调查不到「它从哪知道的」 |
| 在提示词里能写清的要求 | **都不用** | 提示词能解决就别上复杂的 |
| 输出格式要极度稳定（如严格 JSON） | 微调 ✅ | 提示词管不住的稳定性，微调能管 |
| 要用小模型替代大模型省钱 | 微调 ✅ | 这是微调最主要的商业价值 |
| 数据敏感、不能外传 | 微调 ✅⚠️ | 但要注意训练数据会进模型内部 |

### 🔴 最常见的错误

> **拿微调去记业务知识。**

为什么错：**① 不准**（微调学的是倾向，不是精确知识）
**② 一更新就要重训**（文档改了，你还得重新准备数据、重新训练一遍）
**③ 查不到依据**（面试官问「这个答案你哪来的」，你答不上）

**一句话记住**：
> **要知识用 RAG，要习惯用微调，提示词能解决就别上这两个。**

## 7. 面试怎么答（照着说就行）

**问：「微调和 RAG 有什么区别？」**

> 「它们解决的是不同的问题。RAG 管的是『知不知道』——把资料检索出来，在提问的时候递给模型，
> 知识留在外面，文档更新了换个文件就行。微调管的是『怎么说话』——拿自己的例子重新训练模型，
> 改变的是输出的风格、格式习惯，不是给它装知识。
>
> 实际工程里，微调最主流的用法其实是**用小模型替代大模型来省钱**——先用大模型跑通场景，
> 收集几千条好回答，再拿这些数据微调一个小模型。而且现在说微调，默认都是 **LoRA** 这种，
> 不会去动整个模型的参数。
>
> 所以判断很简单：要业务知识、会变的资料，用 RAG；要格式稳定、要省钱，才考虑微调。
> 最常见的错误是拿微调去记业务知识——那样既不准，文档一更新还得重训。
>
> **一句话：RAG 给的是知识，微调改的是风格和习惯，提示词能解决就别上这两个。**」

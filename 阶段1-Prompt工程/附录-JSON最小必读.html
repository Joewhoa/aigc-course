一、JSON 是什么（一句话）

一种把「一条信息」写成机器和人都能读的格式。

它不是编程语言，是一种写法。长这样：

{
  "name": "张三",
  "age": 30,
  "is_manager": true
}

读法：大括号包着一堆「名字：值」。名字叫字段名（name），冒号后面是值（"张三"）。

二、只有两种骨架 + 几种值

骨架只有两个

骨架 长什么样 干什么
对象 { } 装一条信息（一组字段）
数组 [ ] 装一串东西（多条信息）

就这两个。 复杂结构都是它们套娃套出来的。

值有类型（这是重点）

类型 例子 备注
字符串 "张三" 必须带引号
数字 30 不带引号
布尔 true / false 只有这两个，不能写「是/否」
数组 [1, 2, 3] 一串
对象 { ... } 一组
空 null 表示「没有」

最容易错的一条：数字不要加引号。
"age": "30"（字符串）和 "age": 30（数字）是两回事——前者不能做加法，程序会崩。

三、为什么 AI 场景到处都是它

一句话：因为它是「可判定」的。

模型输出一段随便写的文字，程序没法可靠地读；
模型输出 JSON，程序能一条条取出来用。

教材里说得更狠（李博杰第 8 章）：

「如果任务要求输出 JSON 或工具调用，而模型吐出的是无法解析的文本，
奖励函数连「成功还是失败」都判断不了。」

所以它不是「一种格式偏好」，是自动化能不能成立的前提：

  • 工具定义用它（JSON Schema 描述参数）
  • 提示词约束用它（阶段 1 的 1.4）
  • 记忆存储用它（阶段 2 的 2.6）
  • 安全校验用它（教材：「安全检查只看结构化数据，不看模型自由生成的文本」）

四、四条设计铁律（背下来）

# 铁律 不遵守会怎样
1 字段名拼写固定 程序按名字读，错一个字母 = 这个字段不存在，静默丢数据
2 每个字段标类型 数字写成字符串 → 程序算不了
3 枚举值列死 只写「类别」不列取值 → 模型会自己发明不在列表里的
4 分层 明细和汇总混在一起 → 程序没法逐条处理

五、一个完整的例子（前后对比）

场景：批量给图片换色，要它报告结果。

❌ 差的写法：「输出 JSON」

→ 它每次给的字段名都不一样：有时 success、有时 ok、有时 count。
程序没法读。

✅ 好的写法：

输出 JSON，不要输出任何 JSON 之外的内容：

{
  "results": [
    {
      "file": "字符串，文件名",
      "status": "成功 / 失败",
      "reason": "字符串，失败原因；成功时为空"
    }
  ],
  "summary": {
    "total": 数字,
    "success": 数字,
    "failed": 数字
  }
}

四条铁律全在里面：字段名拼写固定（success 不是 sucecss）、每个字段标了类型、
status 和 reason 的取值给了范围、results（明细）与 summary（汇总）分开两层。

六、你不写，但你要会验收（这才是重点）

按你定的规矩：JSON 由 AI 写，你负责验收。 所以你要认得这五处：

查什么 怎么一眼看出来
字段名 跟你要的一不一样？有没有拼错
类型 每个字段标了类型吗？数字有没有被写成字符串
取值 「类别」这类字段，取值是列死的清单，还是含糊的「等」？
层级 明细和汇总分开了吗？还是全塞在一个数组里
约束 有没有写「不要输出 JSON 之外的内容」（不写它会加一堆解释）

认这五处，不需要你会写一行 JSON。

七、一句话收口

JSON 是「让程序能接住模型输出」的接口。
设计它、验收它，是你的活；手写它，是 AI 的活。

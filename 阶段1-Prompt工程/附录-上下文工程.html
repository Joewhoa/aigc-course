阶段 1 附录：上下文工程（Context Engineering）

日期：
为什么有这一节：阶段 1 讲的是「怎么写一条提示词」。但行业术语已经往前推了一步——
面试官现在更可能问的是「你怎么管理上下文」，而不只是「你怎么写提示词」。
一个词的差别，但它是面试官衡量你「跟不跟得上行业」的信号。
阅读重点：1.3 上下文里都放了什么 和 1.4 四个管理动作。

1.1 先分清两个词：Prompt 工程 vs 上下文工程

Prompt 工程 上下文工程
关心什么 一条提示词怎么写好 模型这一次能看到的所有内容，怎么组织
范围 单条指令的措辞、结构、例子 指令 + 历史对话 + 检索到的资料 + 工具定义 + 工具返回结果……
类比 怎么写好一封信 怎么安排整张办公桌，让最重要的东西在最顺手的位置

一句话区别：

Prompt 工程是「怎么把一句话说好」；上下文工程是「怎么把一张桌子摆好」。

桌子上的东西包括：系统指令、对话历史、检索到的资料、可用工具清单、工具返回的结果。
这些全都要挤进同一个上下文窗口。

1.2 为什么这个概念会火起来

因为它解决的是阶段 0 埋下的那个根本矛盾：

模型没有记忆，上下文窗口有限，超出就丢最早的内容。

于是所有「想让模型表现好」的努力，最终都归结为一个问题：

在这一窗有限的容量里，我该放什么、不该放什么、放哪个位置？

这就是上下文工程。

1.3 上下文里都放了什么

一次调用发出去，上下文里通常有这几块：

块 内容 谁放的
系统指令 「你是什么角色、必须遵守什么」 开发者写死
可用工具清单 有哪些工具、参数是什么（阶段 3 第 1 步） 程序注入
对话历史 前面几轮说了什么 程序累积
检索到的资料 RAG 找到的片段（阶段 2 第 ⑤ 步） 程序注入
工具返回结果 上一步工具跑出来的东西（阶段 3 第 5 步） 程序注入
用户当前输入 这次要问的 用户

看出来了吗：真正「用户说的那句话」往往只占很小一块。上下文工程主要管的，是其他五块。

一个重要拆解：静态前缀 + 轨迹

把上面六块按「会不会变」重新切一刀，得到两个部分：

Agent 的上下文 = 静态前缀 + 轨迹

部分 包含什么 会不会变
静态前缀 系统提示词 + 工具定义 一次确定后基本不变
轨迹 用户消息 + 模型回复 + 工具执行结果 每轮都在增长

这个拆解为什么重要：因为它直接决定了你该怎么排序——
不变的放前面，会变的放后面。 下一节的 KV Cache 会告诉你为什么。

1.4 四个管理动作

动作一：挑选——只放相关的

上下文是稀缺资源。塞进去的每一段无关内容，都会稀释有效信息。

  • RAG 要限制 top-k（阶段 2 失效模式 4：找到太多，噪音淹没信号）
  • 对话历史不该全放，只放相关的几轮

动作二：压缩——把长的弄短

手段 做法
摘要 把长对话历史压成一段摘要再放
裁剪 工具返回的长结果只保留关键字段
结构化 用 JSON 代替大段自然语言（信息密度更高）

动作三：排序——重要的放对位置

实践中发现一个现象（俗称「中间迷失」）：

放在开头和结尾的内容，模型记得更牢；放在中间的容易被忽略。

所以：

  • 最关键的约束放结尾（阶段 1 讲过这条）
  • 最重要的资料别埋在中间

动作四：隔离——别让它们互相打架

问题 做法
用户输入里可能藏着指令（阶段 5 的提示词注入） 用户输入和系统指令分开标注，让模型能区分
多轮对话越滚越长 定期把历史压成摘要，或开新会话

1.5 为什么「排序」能省钱：KV Cache

1.4 说了「重要的放对位置」。这一节讲另一个排序理由——钱。

先说 KV Cache 是什么

模型生成文字前，要先读一遍你给的整个上下文，把中间计算结果存下来。
存下来的这个缓存，就叫 KV Cache。

下一次调用时——如果开头部分没变，这段缓存可以直接复用，不用重算。

为什么这很关键：不用重算 = 更快 + 更便宜。

关键约束（一条就能决定你的设计）

KV Cache 只能复用「从开头开始、连续相同的」那一长串。
这串里只要有一个字变了，从那个字往后全部要重算。

用大白话说：它只认「从头开始的相同前缀」。 中间改一个字，后面全废。

一个真实事故（这个例子值得记住）

有人在系统提示词里放了一句：

Current time: {{now}}

为什么这是错的：{{now}} 每次都不一样，等于把变化的东西放在了最前面——
于是整段 KV Cache 每轮都失效，全部重算。

后果：首字延迟从 0.5 秒飙到 3～5 秒，月度账单翻倍。

这就是「排序影响成本」的真实机制。

三条实践规则（背下来，面试能用）

# 规则 为什么
1 系统提示词和工具定义一旦确定，不要随意改动 它们在最前面，一改整段缓存全废
2 动态信息（当前时间、用户输入）放到消息末尾，不要放进系统提示词 变化的东西放后面，前面的缓存就保住了
3 用标准 API 格式组织消息 有些非标准写法（比如把系统提示塞进对话历史）会导致缓存无法匹配

顺带一个名词：Prompt Cache

上面说的是单次对话内部的缓存。还有一层是跨请求的：
同样的前缀在多次不同请求之间也能复用，这叫 Prompt Cache（上下文缓存）。

它的效果有多好：读取缓存的成本大约是首次计算的 1/10。

所以结论：把稳定的内容放前面、把变化的内容放后面——
这个设计一次做对，成本和延迟能差好几倍。

这条对面试的价值

如果有人问「你怎么控制成本」，只答「用便宜的模型」是入门答案。
能答出「我把系统提示词和工具定义固定下来，让 KV Cache 能命中，
缓存读取成本只有首次的十分之一」——这是有工程经验的答案。

1.6 Agent Skills：把「全量加载」改成「按需查阅」

问题是什么

工具和知识越多，全塞进上下文就越糟：

  • 占 token → 贵
  • 内容太长，真正重要的被稀释 → 模型抓不住重点
  • 每次变动都击穿 KV Cache → 缓存失效（见上一节）

解法：渐进式披露（Progressive Disclosure）

不让全部内容常驻上下文，只放一个简短的目录；需要时再加载完整内容。

全量加载 Agent Skills 方式
上下文里放什么 所有技能的完整内容 只放技能名 + 一句话描述
什么时候加载完整内容 一直占着 确定要用时才读进来
类比 把整本书背下来 先看目录，用到再翻那一章

这就是「按需查阅」的思路。

你其实每天在用

WorkBuddy 的技能（Skills）就是这个机制——
一堆技能放在那里，每个只用一句话描述；你让我用某个技能时，我才会去读它的完整内容。

所以这块你有实操，只是以前没有概念名。 面试时可以说：
「我日常用 Agent Skills 这种按需加载的机制来管上下文，
它把全量加载变成按需查阅，既省 token 又不冲淡重点。」

1.7 行业术语的阶梯（面试用它显得跟得上）

「提示工程」这个词已经不够用了。行业里已经往上叠了几层，一层包一层：

提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程

层 管什么 关注范围
提示工程 一句话怎么写好 单条指令
上下文工程 这一窗内容怎么组织 整个上下文
Harness 工程 模型怎么运行、怎么和环境交互 Agent 边界内、模型之外
Loop 工程 循环怎么编排 整个执行循环
Graph 工程 多个循环怎么组成一张图 单 Agent 循环只是图里的一个节点

它们不是替代关系，是层层包含：提示工程是上下文工程的子集，
上下文工程是 Harness 工程的子集……每上一层，工程师能影响的边界就更大一圈。

书里给的核心判断（可以直接拿去面试）：

「当各家模型的能力越来越接近、不再是决定性的差异因素时，
竞争优势就转移到了模型之外的工程实践。」

这一句话是你面试的加分项——它说明你知道「该往哪儿使劲」。

1.8 和前面几阶段的关系

上下文工程不是新东西，它是把前面学的内容收口：

前面学的 在上下文工程里是哪一块
阶段 0 的 Token / 上下文窗口 这是约束条件（桌子就这么大）
阶段 1 的四段式 这是系统指令部分的写法
阶段 2 的 RAG 检索 检索结果就是要放上桌的资料
阶段 3 的工具清单和返回结果 这是桌面上另一大块内容
阶段 5 的提示词注入防御 这是隔离动作

所以这一节的位置是对的：学完阶段 1 的「怎么写」，这里补上「怎么摆」。

1.9 面试会怎么问

面试官问 别这么答 该这么答
「你怎么写提示词？」 只讲措辞 先讲提示词结构（角色/任务/约束/格式），再讲上下文里还放了什么
「上下文工程和 Prompt 工程什么区别？」 「差不多吧」 「Prompt 工程管一句话怎么写；上下文工程管整张桌子怎么摆——包括历史、检索资料、工具清单这些」
「上下文太长怎么办？」 「换个窗口大的模型」 说四个动作：挑选、压缩、排序、隔离；换大窗口只是拖延，不是解决
「为什么关键约束要放结尾？」 「习惯」 「开头和结尾的注意力更高，中间容易被忽略」
「你怎么控制成本？」 「用便宜的模型」 ⭐ 说前缀缓存：系统提示词和工具定义固定不动、动态信息放末尾，让 KV Cache 能命中，缓存读取成本约首次的 1/10
「怎么给 Agent 加技能？」 「都塞进提示词」 ⭐ 说 Agent Skills 的渐进式披露：只放技能目录，用到才加载完整内容

本节要带走的三句话

  1. Prompt 工程管一句话；上下文工程管整张桌子。 行业术语已经往前推了一步。
  2. 上下文是稀缺资源。 挑选、压缩、排序、隔离——四个动作都是为了「在这一窗里放对东西」。
  3. 排序影响成本：不变的放前面、会变的放后面，KV Cache 才命中。缓存读取成本约首次的 1/10。
  4. 「提示工程 → 上下文工程 → Harness 工程 → Loop 工程」是层层包含的阶梯。
    模型能力在商品化，竞争优势转移到了模型之外的工程。

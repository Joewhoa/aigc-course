二、简答题（每题 1 分，共 6 分｜答到要点就给分）

Q7
用六步说清工具调用的完整机制，每步一句话。
考点：3.2
考点：3.2。要点（六步，缺一步扣分）：
① 给模型一份工具清单（有哪些工具、各干什么、要什么参数）
② 模型决定用哪个工具、参数填什么
③ 模型输出一段结构化文本（通常是 JSON）——注意，这只是「说」，不是「做」
④ 外层程序解析这段文本，真的去执行那个工具
⑤ 外层程序把执行结果塞回上下文
⑥ 模型基于结果继续：要么再调一个工具，要么给出最终回答
Q8
什么是 ReAct？
它和「想完再做」相比，好在哪、贵在哪？
考点：3.3
考点：3.3。要点：
· 是什么：ReAct = Reasoning + Acting，即「想 → 做 → 看」三步循环，看完结果回到第一步
· 好在哪：模型的「想」会出错，每做一步看一眼结果，下一步就能及时纠偏；「想完再做」中间错了它不知道，可能一直错下去
· 贵在哪：每一步都要调一次模型，调用次数多，所以更慢更贵
· 判断标准：步骤确定、不怎么会变 → 一次性规划更划算；情况会变 → 用 ReAct
Q9
Agent 有四道防线：权限最小化 / 高风险确认 / 参数校验 / 轮次与成本上限。
请挑其中两条，各说明它防的是什么问题。
考点：3.4
考点：3.4。参考答案（任两条成立即可）：
· 权限最小化：防「它不该做的事」。只给必须的工具，不需要删文件的权限就别给
· 高风险确认：防「做了就不可逆的事」。删除、发送、付款、重启服务 → 先问人再执行
· 参数校验：防「参数填错填坏」。程序在执行前检查参数合法性（比如路径是否在允许范围内）
· 轮次与成本上限：防「死循环烧钱」。设最大循环次数、单次任务设 token 上限
Q10
有句话叫「护栏分三层：上下文层 / 执行层 / 数据层」。
请说明 ① 为什么「越往下越硬」；② 为什么光是上下文层给不了保证。
考点：3.4
考点：3.4。要点（两问都要答到）：
· ① 为什么越往下越硬：三层是按「有多难被绕过」排的，不是按先后顺序。上下文层拦「模型能看到什么」、执行层拦「模型能做什么」、数据层管「世界最终能被改成什么样」。越往下越不靠模型自己判断，所以越难被一次攻击打穿
· ② 为什么上下文层给不了保证：处在同一个上下文里的 Agent，很难判断自己是不是已经被注入。恶意指令如果藏在网页、文档、工具描述里混进上下文，Agent 自己分辨不出来。所以上下文层只能降低成功率，给不了保证
· 加分：能点出「真正兜底的是数据层——就算模型被骗了，它手上的凭证也不允许它做那件事」
· ⚠️ 若只答「三道护栏分别是什么」而不答这两问，不给分
Q11
什么是「Agent 的上下文 = 静态前缀 + 轨迹」？
这两块各自的特性是什么、对工程有什么影响？
考点：3.2
考点：3.2。要点：
· 是什么：模型每一轮看到的上下文分两块——静态前缀（系统提示词 + 工具清单）+ 轨迹（用户消息 + 模型回复 + 工具返回）
· 静态前缀的特性：一次任务里基本不变 → 所以能被缓存（省钱、加速）
· 轨迹的特性：只增不减，每跑一轮就长一截 → 所以任务跑得越久越贵
· 工程影响：这就是为什么需要「上下文压缩」和「轮次/成本上限」；也是回答「Agent 的上下文怎么管」时的标准切口
· ⚠️ 只答出两块名词、说不出「不变→可缓存 / 只增→越跑越贵」，扣一半

Q13

面试官问你：「什么时候你会用 Agent？」

要求：成段说，不要分点符号。 要包含编排模式的选择判据（工作流 vs 自主）。
考点：3.6

考点：3.6。要点（成段说，要包含选择判据）：
· 从简单到复杂，第一个「是」就是答案：① 单个模型调用能解决吗？→ 就一次调用，别搞编排 ② 能清晰分解成固定的子任务吗？→ 工作流（步骤写死） ③ 步骤数不确定、需要边走边看吗？→ 自主 Agent
· 为什么不该上来就自主：自主更贵、更慢、更难控制；Agent 系统是用延迟和成本换任务性能
· 工作流的优势：执行路径确定 → 流程控制严格、更安全（攻击面被限制在单个节点内）
· 加分：提到「实际项目里常常混着用——关键流程用工作流兜底，灵活的部分放自主」
· ⚠️ 若只答「Agent 更智能所以能用就用」，不给分
Q14

你的 Agent 老是选错工具（该用 A 的时候用了 B）。
请说明你第一步会去查什么、为什么；并说出工具描述该写清哪两件事。
考点：3.7

📎 3.8 是面试汇总节，内容全部由 3.1–3.7 的答案拼成，不单独出题（重复考没有意义）。

考点：3.7。要点：
· 第一步：先改工具描述，不是换模型。大多数工具选错的根因是描述不准确（边界不清、缺少反例、参数含义模糊），改描述的投入产出比远高于换个更强的模型
· 描述该写清的两件事：① 什么时候用——不是「这个工具能做什么」，而是「什么情况下该选我」 ② 边界与反例——做不到什么、不接受什么输入；大多数调用失败的根因不是不知道能做什么，而是不知道不能做什么
· 加分：提到「附 1–5 个真实调用示例，准确率约 72% → 90%」或「参数描述用具体例子代替抽象规范（如 E.164 格式 + 一个真实号码）」

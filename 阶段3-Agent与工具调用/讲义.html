阶段 3 讲义：Agent + 工具调用

本阶段目标：讲清 Agent 是什么、它怎么动手、以及怎么管住它。
如果你见过「用自然语言控制设备 / 电脑」这类东西，这一阶段会把它拆开看。
阅读重点：3.2 六步机制 和 3.4 四道防线 + 三层护栏。

3.1 Agent 和「会聊天的模型」差在哪

大多数人对 Agent 的理解是「更聪明的聊天机器人」。这个理解会漏掉最关键的机制。

真正的区别是：Agent 多了一个循环。

普通模型调用 Agent
过程 你问 → 它答 → 结束 你问 → 它决定做什么 → 执行 → 看结果 → 再决定下一步 → …… → 完成
轮次 一次 可能很多次，直到它认为任务完成
能不能动手 不能，只会说 能，通过工具

关键在那个「看结果再决定下一步」。 这就是 Agent 的本质，而它需要一个「循环器」来一遍遍跑——那个循环器就是我们阶段 0 讲过的 harness。

一句话：Agent = 模型 + 工具 + 循环。

Agent 的另一半：环境

上面那张表只讲了 Agent 这一侧。但它循环的时候，总得有个对手——那个对手叫环境。

环境包括：文件、数据库、网页、你的手机、用户本人、甚至物理世界。
Agent 只能通过两个口子和它打交道：

口子 一句话解释 例子
观察空间 Agent 能看到什么 读到的文件内容、网页、屏幕截图
动作空间 Agent 能动手做什么 跑命令、写文件、点按钮、发消息

没进观察空间的信息，对模型来说等于不存在；没被动作空间允许的操作，模型知道了也只能干说。

这句话有个很实际的推论——

模型不变的前提下，让 Agent 变强最有效的办法，往往是重新划一遍这两个空间：
把需要的数据塞进观察空间，把要做的动作封成工具。

举两个具体例子：

  • 给 Agent 多加一个「读本地文件」工具 → 它的动作空间扩了，原来够不着的东西现在能读。
  • 把项目规范写进系统提示词 → 它的观察空间扩了，原来不知道的规矩现在知道。

这就是为什么「换个更强的模型」经常不是答案——很多时候不是模型笨，
是该给它看的没给它看、该让它做的没做成工具。

一个真实的产品演进例子：

早期的 Agent 大多只干一件事——要么只做深度调研、要么只写代码。
后来 Manus 把「虚拟浏览器 + 文件系统 + 代码执行」放进同一个 Agent，
等于把三种能力的观察空间和动作空间并成了一份，于是它能跨着原来的产品边界干活。
它靠的不是换模型。

3.2 工具调用的完整机制（六步）

这是本阶段的核心。

步 谁在做 做什么
1 你（或程序） 给模型一份工具清单：有哪些工具、各干什么、需要什么参数
2 模型 根据你的问题，决定「用哪个工具、参数填什么」
3 模型 输出一段结构化文本（通常是 JSON）——注意，这只是「说」，不是「做」
4 外层程序 解析这段文本 → 真的去执行那个工具
5 外层程序 把执行结果塞回上下文，再次发给模型
6 模型 基于结果继续：要么再调一个工具，要么给出最终回答

第 3 步和第 4 步的区分是整条链的关键

回到阶段 0 那条边界：模型只输出文字，执行永远发生在外层程序里。

模型在这一步做的，仅仅是「用约定好的格式声明我要调用哪个工具」。真正去调用的是 harness。

为什么工具调用要用 JSON

因为要让程序能可靠地解析你填的参数——这是阶段 1 讲的「可判定性」。

阶段 1 的附录专门补了 JSON，就是为了这里。工具调用的参数、返回值，全是结构化数据；
不会读 JSON，就没法理解 Agent 到底在干什么。

两个值得记住的术语：静态前缀 和 轨迹

上面六步跑起来之后，模型每一轮看到的东西其实分成两块：

术语 里面装什么 会不会变
静态前缀 系统提示词 + 工具清单（也就是第 1 步那份） 一次任务里基本不变
轨迹 用户说了什么 + 模型回了什么 + 工具返回了什么 每跑一轮就长一截

合起来一句话——Agent 的上下文 = 静态前缀 + 轨迹。

为什么要记这两块：

  • 静态前缀适合放那些「从头到尾都用得着」的东西，而且它不变，就能被缓存（省钱、加速）。
  • 轨迹只增不减，所以任务跑得越久越贵——这就是为什么需要「上下文压缩」和「轮次上限」。

这两块正是回答「Agent 的上下文怎么管」时最该先说清楚的。

3.3 ReAct：边想边做

ReAct = Reasoning（推理）+ Acting（行动）。它是 Agent 最主流的思考框架。

循环三步，来回转：

步 名字 干什么
1 Thought（想） 我现在该干什么
2 Action（做） 调用工具
3 Observation（看） 工具返回了什么

看完结果，回到第 1 步，再来一轮。

和「想完再做」的对比

想完再做 ReAct（边想边做）
规划方式 一次规划全部步骤，然后逐步执行 每做一步看结果，再决定下一步
出错了 中间错了不知道，可能一直错下去 下一步能及时纠偏
成本 便宜（调用次数少） 贵（调用次数多）

为什么要 ReAct：因为模型的「想」会出错。让它每一步都看一眼结果，能自己发现并调整。

ReAct 的一个实例

手机（或任意客户端）发指令 → 模型出意图 → harness 执行 → 模型看到执行结果 → 再决定下一步。
那个「看结果」的环节，就是 ReAct 里的 Observation。

3.4 怎么保证 Agent 不乱来（四道防线 + 三层护栏）

Agent 能动手 = 有风险。这是它和聊天模型的第二个人造区别。

# 防线 兜住什么 做法
1 权限最小化 它「不该做」的事 只给它必须的工具。不需要删文件的权限，就别给
2 高风险确认 做了就不可逆的事 删除、发送、付款、重启服务 → 先问人再执行
3 参数校验 参数填错、填坏 程序在执行前检查参数是否合法（比如路径是否在允许范围内）
4 轮次与成本上限 死循环烧钱 设最大循环次数；单次任务设 token 上限

第 2 防线的一个真实实例

很多 Agent 项目的约定里会写：

「任何涉及关闭或重启进程的操作，都必须先提交审批让用户确认，不得擅自重启」

这就是标准的「高风险动作要确认」——因为重启是不可逆的、会中断服务的。

⚠️ 四道防线管不了的一种情况：工具失败了怎么办

现象 原因 怎么避免
模型反复调用同一个失败的工具，试到轮次耗尽 错误信息不可执行——只告诉它「失败了」，没告诉它「接下来能做什么」 错误信息里必须写清替代路径

举个对比：

❌ 不可执行的错误 ✅ 可执行的错误
Error: file not found 文件 /data/a.csv 不存在。可用文件：a.csv（当前目录）、b.csv（上级目录）。请改用其中一个重试。
Error: 403 Forbidden 没有读 /admin 的权限。可读范围：/public、/data。需要更高权限请向管理员申请。

区别在哪：左边只说了「出事了」，模型只能猜或原地重试；
右边告诉它还能做什么——它才能自己绕过去。

这条是四道防线的补充，不是并列：四道防线管的是「该不该做」，
这一条管的是「做失败了怎么恢复」。缺了它，Agent 会在死胡同里反复撞墙，
直到撞满轮次上限（防线 4）才停——烧掉的全是真金白银。

为什么这四条最该记

多数人复盘时只会说「我做了个 Agent」，不会说「我怎么管住它」。
能讲清这四道防线，说明做过真实的东西，而不只是跑过 demo。

但这四道还不够：护栏有三层

刚才那四道防线，其实是同一个位置上的四件事——它们都在拦「Agent 要动手的那一刻」。
真正的防护不是一个点，是三层。这三层不是按先后顺序排的，是按「有多难被绕过」排的：

层 管什么 什么时候起作用 例子
第一层：上下文层 模型能看到什么 内容还没进模型之前就拦掉 过滤越狱/注入的输入、屏蔽无关问题、长度限制
第二层：执行层 模型能做什么 动作真要生效之前校验 我们上面那四道防线都在这层、给工具标风险等级、敏感数据打码
第三层：数据层 世界最终能被改成什么样 数据落到库里那一刻 数据库的行级权限、只读视图

越往下越硬——因为越往下，越不靠「模型自己判断」，也就越难被一次攻击打穿。

为什么必须有下面两层？资料里给了一句很关键的话：

处在同一个上下文里的 Agent，很难判断自己是不是已经被注入。

意思是：光在它看见的东西上设防，是有天花板的。攻击者的恶意指令如果藏在网页、
文档、别人的工具描述里混进上下文，Agent 自己分辨不出来。
所以第一层只能「降低成功率」，给不了保证。真正兜底的是：就算模型被骗了，
它手上的凭证也不允许它做那件事（比如给它一个只能读的账号）。

这一层怎么表述才到位：

「我的做法是在执行层做权限最小化 + 高风险确认；
但我也知道执行层不是最后一道——真正兜底的是数据层的权限，
因为那一层不依赖模型判断，模型被骗了也越不了权。」

能说到「数据层不依赖模型判断」这一句，就明显区别于只会背四道防线的人。

行业术语：这套东西有个正式名字，叫 Harness

阶段 0 埋过一个伏笔：生产环境下 Agent = Model + Harness。这里收口。

Harness = 模型之外、Agent 之内的那层工程代码。它包含五个部分：

Harness 五要素 干什么 对应我们学的
上下文管理 给模型足够的感知信息 阶段 1 附录 + 阶段 2
工具接口 给模型清晰可用的手脚 3.2 六步机制
约束 限定它能做什么、不能做什么 3.4 权限最小化
验证 检查它做得对不对 3.4 参数校验 + 3.5 验收条件
纠正 做错了怎么补救 3.4 轮次上限 + 5.2 错误恢复

看出来了吗——我们的「四道防线」，就是它的「约束 / 验证 / 纠正」三要素。
我们没讲错，只是用词不一样。它这套用词是当前行业的通用语言，
用它的词来表述会更通用。

为什么 Harness 是「竞争力」（资料里给的实例）：

LangChain 在一个终端任务的评测基准上，把得分从 52.8% 提到 66.5%
（排行榜从 30 名开外进到前 5）。改的不是模型，是 Harness——
让 Agent 自动检查自己的执行结果、检测是否陷进重复循环、优化思考策略。

一句话概括：

「模型能力正在商品化，真正的差异化在模型之外的工程——
也就是 Harness：上下文怎么管、工具怎么给、怎么约束、怎么验证、出错怎么纠正。」

另一条佐证：Claude Code 这类产品的 Harness 里，绝大部分代码都在做约束、验证、纠正，
工具本身（读写文件、跑命令）只占很小一部分。管住 Agent，才是工程的重点。

3.5 怎么证明它干对了：测试驱动开发

Agent 会动手，动手就可能出错；而人眼是检查不过来的（处理 1000 张图你怎么看）。

TDD（测试驱动开发）的核心顺序：

  1. 先写验收条件——写清「什么样的结果算合格」
  2. 跑一次 → 应该失败（这一步很关键，它证明这个条件确实在检查东西）
  3. 让 AI 实现 → 再跑 → 通过才算完成

为什么顺序不能反过来

  • 先写实现，再补测试 → 测试很容易写成「实现干了什么就测什么」，测了个寂寞
  • 先写测试 → 测试就是需求，实现必须满足它

两个最容易犯的错

反模式 表现 怎么避免
同义反复 期望值是从实现代码反推出来的，所以测试永远通过，永远发现不了问题 期望值要来自独立来源：手算出的已知结果、真实样本、别人给的答案
水平切片 一口气写完所有测试，再开始写实现 一次只做一个：一个测试 → 一个实现 → 再来下一个

不写代码的人怎么用

用大白话写验收条件，让 AI 去写测试。

举例——一个批量处理图片素材的脚本：

① 非目标像素的 RGB 必须和原图完全一致
② 输出目录的文件数等于输入目录
③ 处理失败的图必须出现在清单里，不许静默跳过

这三条就是验收条件，也是验收 AI 干活的标准。 不写代码，但能写这三条。

为什么这条重要

能说「我先定验收条件，再让 AI 实现，最后跑一遍验证」——
这比说「我让 AI 写了个脚本」高一个层次。前者是管理结果，后者是许愿。

3.6 编排模式：工作流 vs 自主 Agent（★ 本阶段最该记的一节）

前面五节讲了 Agent 怎么工作、怎么管住它。但有个更重要的问题还没回答：

什么时候该用「自主 Agent」，什么时候根本不该用？

很多人学完 Agent 就什么都想做成自主的。这是错的方向。 有两种编排模式：

工作流（Workflow） 自主 Agent（Autonomous）
执行路径 预先定义好，按固定代码路径走 实时决定，根据环境反馈动态走
模型干什么 只在每个节点内部做理解和生成 自己决定下一步做什么、做几步
适合什么 能清晰分解为固定子任务的场景 开放式、步骤数难预测的任务
优势 严格的流程控制 + 安全（攻击面被限制在单个节点内） 灵活，能应对意外情况
局限 缺乏变通性 更贵、更慢、更难控制

选择判据：从简单到复杂

按这个顺序问，第一个「是」就是答案（跟阶段 0 的五问表同一个思路）：

顺序 问自己 是 → 用什么
1 单个模型调用能解决吗？ 就一次调用，别搞编排
2 能清晰分解成固定的子任务吗？ 工作流——步骤写死，模型只在里面干活
3 步骤数不确定、需要边走边看吗？ 自主 Agent

资料里的原话：「对于可以清晰分解为固定子任务的场景，考虑使用工作流。
只有当需要动态决策和灵活的执行路径时，才使用自主 Agent。」

📌 补一句：「能不能拆成固定的子任务」这件事本身就是一项能力——
拆得对不对，直接决定了上面第三步往哪走。这项能力叫任务拆解，
我们在阶段 5 讲 Harness 时会正式讲（怎么把一个模糊的大目标拆成一串可验收的小步）。
这里先记住：它是「选编排模式」的前置动作，也是最容易被顺手问的一句。

还有一句要记住：「Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡。」

混合模式（实际工程里最常见）

不是二选一，可以混：

混法 怎么用
关键流程用工作流，灵活部分用自主 「有严格合规要求的流程用工作流确保可靠性，需要灵活决策的部分切换到自主模式」
先自主、后固化 「先由自主 Agent 把工作流写出来，再由工作流去执行」——先用自主探路，摸清套路后固化成便宜的工作流

第二种混法特别值得记：它的意思是——
自主 Agent 不只是产品，也是「设计工作流的工具」。 让它先跑几遍，你观察它走的路径，
然后把稳定的路径固化成工作流。这是从贵到便宜的演进路径。

一个例子

需求 选什么 为什么
「把用户留言分成 5 类打标签」 单次调用 一步就能干
「收到发票邮件 → 提取信息 → 录入系统 → 发确认邮件」 工作流 步骤固定，顺序明确
「帮我修这个 bug」 自主 Agent 不知道要改几个文件、要试几轮
「研究一下这个行业的竞争格局」 自主 Agent 搜几次、看哪些资料，事先说不准

为什么这一节最重要

「什么时候你会用 Agent」——这是个筛子题。

只会答「Agent 更智能所以能用就用」的，是不懂。
能答「能确定流程的就别上自主，因为延迟和成本更高、还更难控制」的，是懂。

一句话概括：

「我按从简单到复杂来选：先看单次调用够不够，其次看能不能拆成固定流程——
能拆就用工作流，因为执行路径确定、更安全也更便宜；
只有当步骤数事先说不准、必须边走边看时才上自主 Agent。
实际项目里常常混着用，关键流程用工作流兜底，灵活的部分放自主。」

3.7 工具的五种类型（以及工具该怎么设计）

3.2 讲了「工具调用怎么发生」。这一节讲「工具本身该怎么分类、怎么设计」——
这是从「会用 Agent」到「会设计 Agent」的分界线。

五种类型（按「它和世界的关系」分）

类型 干什么 例子 设计要点
感知工具 主动获取信息、感知世界 网页搜索、知识库检索、抓网页、找文件、搜文件内容、读文件 ⚠️ 关键是控制输出信息量，防止上下文爆炸
执行工具 改变外部世界 跑命令、执行代码、写文件、改文件、发邮件 ⚠️ 错误代价可能极高，安全约束是设计的核心
协作工具 与其他 Agent 或人协作 启动子 Agent、给子 Agent 发消息、终止子 Agent、列出所有 Agent 最简单是并行跑不相关的任务
用户沟通工具 主动向用户传递信息 回复用户、发卡片给用户、发通知 异步多渠道场景下，「说话」本身也要成为显式工具
事件触发工具 让外部世界驱动 Agent 行动 设定时器、监控进程、接入消息渠道 含注册（声明关心什么事件）和触发（被回调唤醒）两个时刻

一句话记住前两类（这是最实用的）

感知工具要小心「话太多」——它会把上下文撑爆。
执行工具要小心「手太快」——它会造成不可逆的后果。

这两条正是 3.4 那四道防线要解决的问题：
感知工具的输出量要控制（对应 5.2 的可观测性、阶段 1 的上下文管理）；
执行工具要有权限约束和确认（对应「权限最小化 + 高风险确认」）。

为什么是五类而不是三类：少了「用户沟通」和「事件触发」，
Agent 就只能被动等你说——不能主动问你，也不能到点自己动。
加上这两类，它才能「主动」。

工具设计的三条通用原则

# 原则 具体怎么说
1 通用工具优于专用工具 一个「读文件」胜过十个「读报表」「读日志」「读配置」。只有四种情况才退回专用：① 安全权限要审计 ② 要屏蔽平台差异 ③ 使用频率极高 ④ 参数结构太复杂
2 描述的重点是「什么时候用」 不是「这个工具能做什么」，而是「什么情况下该选我」。边界条件比能力描述更重要。再配上 1–5 个真实使用例子
3 参数要保真 禁止「静默转换」——模型说传 A，就别偷偷改成 B。模型看到的世界和工具动手的世界，不能有系统性偏差

第 2 条最容易被忽略，也最有用：
如果你的 Agent 老是选错工具，第一件事不是换模型，是去改工具描述。

工具太多怎么办（真实的工程难题）

症状：工具到一百个以上，再先进的模型也容易选错；而且全量平铺在上下文里，
既占 token，每次变动还会击穿缓存（阶段 1 附录会讲 KV Cache）。

三种解法：

解法 怎么做
层次化组织 工具分组，先选组，再选具体工具
主动工具发现 Agent 发现能力缺口时，主动用自然语言说「我需要什么能力」，系统再去匹配注入
Skills 化（按需查阅） 只留少量基础工具 + 一个「工具搜索工具」，需要时再查——本质是把「全量加载」变成「按需查阅」

「按需查阅」这个思路，你可能已经见过：
现在主流的 Agent 工具大多都有「技能（Skills）」机制，用的就是这套——
少量技能索引常驻，完整内容用到才读。
如果你用过这类工具，这块你就有实操，只是现在对上概念名了。

3.8 章节小测：能答上来才算真会了

合上讲义自测。每题答得出来才算真会；答不出来的，回对应小节重读。

自测题 常见误解 正确理解
Agent 和普通调用差在哪？ 「Agent 更智能」 多了循环：能看结果再决定下一步
什么时候该用 Agent？ 「Agent 更智能，能用就用」 ⭐ 编排模式：先看单次调用够不够；能拆成固定流程就用工作流；只有步骤数事先说不准才上自主 Agent
工具调用怎么实现的？ 「模型自己调用的」 说六步链条，强调模型只出请求、程序才执行
怎么防止 Agent 做坏事？ 「加提示词约束」 说四道防线：权限最小化 / 高风险确认 / 参数校验 / 轮次成本上限；⭐ 再往上说一层：这四道都在执行层，兜底的是数据层——因为那层不依赖模型判断
Agent 被提示注入了怎么办？ 「提示词里写清楚别听它的」 ⭐ 说护栏分层：同一个上下文里的 Agent 判断不了自己是否被注入，所以上下文层只能降低成功率；真正兜底的是执行层（凭证 + 人工确认）和数据层（权限）
Agent 老是选错工具怎么办？ 「换个更强的模型」 ⭐ 先改工具描述——重点写「什么情况下该选我」，加真实使用例子
模型之外还有什么可优化的？ 「不知道」 ⭐ 说 Harness：上下文管理 + 工具接口 + 约束 + 验证 + 纠正；⭐ 能再加一句「模型固定时，扩观察空间和动作空间最有效」更好
怎么知道它干对了？ 「看一眼」 先定验收条件 → 跑一次确认会失败 → 再实现 → 跑通才算完成

本阶段要带走的四句话

  1. Agent = 模型 + 工具 + 循环。 那个「看结果再决定下一步」就是它的本质；
    而它循环的对手是环境——模型不变时，扩观察空间和动作空间最有效。

  2. 模型只出请求，执行永远在外层程序。 六步链条要能背下来；
    上下文 = 静态前缀 + 轨迹（轨迹只增不减，所以越跑越贵）。

  3. 能动手就有风险。 管住它靠四道防线（= 行业术语里的 Harness 约束/验证/纠正），
    而四道防线都在执行层——真正兜底的是数据层，因为那层不依赖模型判断。
    证明它干对了靠先定验收条件。

  4. ⭐ 不是所有任务都该用自主 Agent。 能确定流程的用工作流；
    只有步骤数事先说不准，才上自主。模型之外的 Harness，才是真正的竞争力。

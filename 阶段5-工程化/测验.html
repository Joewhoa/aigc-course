二、简答题（每题 1 分，共 12 分｜答到要点就给分）

Q9

① 可观测性要记哪几类东西？
② 为什么不能只看「平均延迟」，而要看 p95？

考点：5.1 / 5.2

考点：5.1 / 5.2。① 可观测性记四类（缺一扣分）：
  · 每次调用的输入 / 输出（复现问题要看当时原文）
  · 工具调用轨迹（错在「选错工具」或「参数填错」）
  · 耗时与成本（定位慢在哪、贵在哪）
  · 失败与重试（区分偶发错与必然错）
② 为什么看 p95 不只看平均：平均延迟会被大量快请求拉低，p95 反映「最慢的那 5% 用户」的真实体验——而那正是最影响口碑的部分。
Q10

① 模型输出交给「守门员」检查时，检查分哪三个层次？
② 为什么不能让守门员自己「修好不合规的值」或「放宽标准」？

考点：5.7

考点：5.7。① 三个检查层次（缺一扣分）：
  · 结构对不对：字段名、字段数、层级（有没有这个键、有没有多出没见过的键）
  · 类型对不对：值的数据类型（金额应该是数字，不能是字符串 "42"——最常见的坑）
  · 值合不合理：取值范围、格式（不能是负数、日期不能是「32 号」）
② 为什么不能让守门员自己修 / 放宽：
守门员会「将就着放行」，它就不是关卡而是摆设——校验的价值恰恰在于「它说不合格就是不合格」。
允许：拦下来、要求重试。禁止：自己修数据、自己放宽标准。
Q11

① 什么是「评估门」？它跟「做一次评测」的区别是什么？
② 「在线评估」补的是离线评估的什么短板？
③ 通过率从 78% 变成 82%，你会怎么判断这个提升是不是真的？

考点：5.3

考点：5.3。① 评估门 vs 做一次评测：
评估门 = 把评测当成发布闸门——不过就不许上线，由结果拍板，而不是「我觉得这次改得挺好」。
区别：「测一下看看」是活动，「不过就不发」是闸门。（确实要带病上线（紧急修复）要留痕，不能默默破例）
② 在线评估补什么短板：离线用固定样本、在上线前；在线用真实用户输入、上线后持续跑，擅长发现实验室无法预见的情况（奇怪输入、新话题、新用法）。
实践：从线上日志定期抽样（如每周 200 条）判一遍，把新问题补进离线评测集。
③ 78% → 82% 怎么判断真假：
· 多跑几轮（同版本跑 3 次看范围，三次是 78/81/79 那 82% 多半不算提升）
· 看差异够不够大（提升幅度要明显大于波动幅度；差 2–3 个点先怀疑）
· 加分：配对分析（同一批题逐条比对，不只看两个总分）
Q12

① 什么是「模型路由」？为什么它能省成本？
② 「限流 / 重试 / 回退」分别解决什么问题？
③ 讲义说「能并行别串行」——这个建议有个前提条件，是什么？

考点：5.4

考点：5.4。① 模型路由：
加一层「任务难度判断」——分类 / 改写 / 抽取这类简单任务走小模型，多步推理 / 需要判断的走大模型。
为什么省：真实请求里简单的那类占多数，让它们走小模型，成本能降一大截而用户几乎无感。
② 三个机制（缺一扣分）：
· 限流：限制每分钟/每天的调用次数或 token 量——防流量突增打光配额、防单用户刷爆
· 重试：自动再试一次——应对偶发错（网络抖动、限流）
· 回退：主模型不可用时切到备选——「A 挂了切 B」，而不是让用户看到报错页
③ 并行的前提条件：
如果后一个工具的参数要来自前一个工具的结果，就只能串行。
（不是「能并行就一定该并行」，判断依赖本身就是一项设计能力）
Q13

① async 异步解决的是什么问题（一句话）？
② Q3 那个「先查天气再决定带伞」的场景，如果硬要并行会发生什么？
③ 并行执行时其中一个失败了，剩下的该怎么处理？

考点：5.9

考点：5.9。① async 解决什么（一句话）：
解决「等待」——3 个工具各等 1 秒，串行 3 秒、并行 1 秒。原理是等待期间去干别的，不是「算得更快」。
② 硬要并行会怎样：
「先查天气再决定带伞」里，第二个调用在第一个结果出来之前根本拿不到参数——
要么拿空值去跑（结果错），要么直接报错。依赖判断错了，并行只会更快地出错。
③ 一个失败了怎么办：
级联中止——A 失败就让 B/C 停（它们的结果已无意义），避免拿到半成品数据。
同时并发数要有上限（不然会打爆配额）。
Q14

① 「类型注解 / venv / 依赖锁定」这三件事，各自解决了什么问题？
② 关于 venv，有哪条常见误解需要纠正？

考点：5.8

考点：5.8。① 三件事各解决什么（缺一扣分）：
· 类型注解：让静态类型检查工具在运行之前就抓出错（最便宜发现的一类 bug，不用等它把数据改坏）
· venv：隔离「装了哪些包」——让依赖不打架（否则换个项目就跑不起来）
· 依赖锁定（requirements.txt / lock 文件写死版本）：让环境可复现（任何人任何时候装出来的都一样）
② venv 的常见误解：
❌「用了 venv 代码就跑在沙盒里，跑不了我的文件、连不上我的网络，很安全」
✅venv 只隔离 Python 包，不限制文件系统 / 网络 / 进程权限——它不是安全沙盒（那是 Docker 之类技术干的活）。
「以为隔离了包就等于隔离了风险」是会误判的。
（教材原话：venv「只隔离包依赖，对文件系统、网络和进程没有任何安全约束」）
Q15

① 容器化解决了哪两个问题？（提示：一个跟「可复现」有关，一个跟「隔离」有关）
② 镜像、容器、volume 分别是什么？
③ 隔离强度分哪三档？按什么判断该选哪一档？

考点：5.10

考点：5.10。① 容器化解决的两个问题（缺一扣分）：
· 可复现：代码在你这跑得好好的、发给别人就报错（Python 版本不同、少装了库）→「程序＋依赖＋配置」打成箱子，到哪都一样
· 隔离：AI 写的代码要跑在机器上，它要是删了你文件、访问了你的网 → 让它跑在隔离空间里
② 三个概念（缺一扣分）：
· 镜像：打包好的模板（静态）≈ 安装包
· 容器：按模板跑起来的实例（动态）≈ 装好并在运行的软件
· volume：把目录挂到容器外面——容器删了数据还在。⚠️ 容器里存的数据、容器一删就没了，这是第一大翻车点。
③ 隔离三档 + 选档判据（缺一扣分）：
· 进程级（最低）：本地跑 ＋ 限制可写范围（工作区沙盒 ＋ 高风险审批）
· 容器（Docker）：独立文件系统 ＋ 网络栈，但共享内核、内核漏洞仍可能逃逸
· microVM / 虚拟机（最高）：带独立内核的硬件级隔离
选档判据：输入不可信 ＋ 凭证敏感 ＋ 操作不可逆 → 即使本地开发也要上容器甚至 microVM；
本地开发且输入可信 → 进程级 ＋ 工作区沙盒 ＋ 审批通常就够。
口诀：venv 隔离依赖 / 容器隔离运行 / microVM 隔离硬件。
Q16

面试官问：「你要改一版 Agent（换模型 ＋ 改提示词），怎么保证它安全上线？」
请给出你的完整做法。

考点：5.11

考点：5.11。成段或分点均可，答到下面几条就给分：
· 先看「能跑 vs 能用」：明确这次改动要解决哪个「能用」的缺口（可观测 / 可评测 / 成本 / 安全）
· 跑评测当闸门：评测集不过就不发（评估门），不是「测一下感觉还行」
· 版本对应：模型版本 ＋ 提示词版本 ＋ 工具版本记清楚
· 灰度：先放 1%–10% 流量
· 观察指标：Trace / 失败率 / 成本 / 延迟（能回滚的前提是有监控）
· 能回滚：指标变差就切回旧版——「能撤回来，才敢改」
· 留版本记录：哪次改了什么、为什么改、效果如何（否则出事不知道是哪次改坏的）
Q17

① 按「谁负责管理这个 Agent」，行业里常分成哪三种模式？各适合什么？
② 一个 Agent 从创建到退役，完整生命周期有哪几步？其中哪一步最容易出事？

考点：5.6

考点：5.6。① 三种模式（缺一扣分）：
· 客户端托管：Agent 跑在用户自己的设备上（个人助手、离线、隐私最严）
· 托管代理：Agent 跑在厂商的服务器上（多数企业应用属于这类）
· 工作流编排：Agent 只是大流程里的一个环节，由工作流引擎统一调度（多步骤、强顺序、要审批的业务流程）
为什么要分清：影响责任边界（出事谁负责）、数据流向（请求经过谁的服务器）、运维成本（谁升级、谁监控）。
② 生命周期六步（缺一扣分）：
创建 → 定版本 → 跑评测 → 部署（灰度）→ 观察 → 退役
· 定版本：模型版本 ＋ 提示词版本 ＋ 工具版本，三者要能对应上
· 评测：过不了评估门就不发（5.3）
· 观察：看 Trace / 指标（5.2），异常就回滚
③ 最容易出事的一步：退役。
很多事故不是「改坏了」，而是「新旧两版并存、下线顺序错了」——
旧版本没被安全下掉、或下掉顺序不对，导致流量打到半废弃的版本上。
Q18

① 容器和虚拟机的根本区别是什么？为什么「容器就是轻量虚拟机」这个说法是错的？
② 为什么 Windows 上装 Docker 必须先装 WSL2？这件事说明了什么？

考点：5.10

考点：5.10。① 根本区别（缺一扣分）：
· 虚拟机带自己的操作系统内核（体积 GB 级、启动分钟级、能跨操作系统跑）
· 容器只隔离用户态（文件系统 / 网络 / 进程），和宿主机共享内核（体积 MB 级、启动秒级、不能跨内核跑）
一句话：虚拟机虚拟的是「整台电脑（含操作系统）」；容器虚拟的是「一个隔离的运行环境」。
加分：「容器是轻量级虚拟机」是错的；而且「轻」和「弱」是同一件事的两面——不虚拟硬件所以省资源，但也共用内核所以隔离有边界。
② 为什么 Windows 装 Docker 必须先装 WSL2：
因为容器要用宿主机提供的 Linux 内核。Windows 内核与 Linux 内核不同，
所以要先装 WSL2，借用它的 Linux 内核来跑容器。
这件事说明的就是「容器不是虚拟机」——如果真是虚拟机，就自带整个操作系统，不需要这个额外步骤。
Q19

① 保证「密钥不进镜像」有哪三道闸？
② 为什么 Dockerfile 里的 ENV 不能写真实密钥值？该改用什么方式传？
③ .dockerignore 和 .gitignore 是什么关系？

考点：5.10

考点：5.10。① 三道闸（缺一扣分）：
· 闸 1：.dockerignore 挡住构建期——不让密钥被 COPY 进去
· 闸 2：运行时用 -e 名字=值 传参——只在运行期生效，不落镜像
· 闸 3：代码里根本不硬编码——压根没有密钥可泄露（最省事的一招）
② 为什么 ENV 不能写真实密钥：
ENV 会明文写进镜像层，docker history 一敲就能看到所有 ENV 的值。
而且删不掉——后加的层不能移除已生成的层（见 Q20）。
→ 该用 -e 运行期传参。
③ 两文件的关系：
作用几乎一样，都声明「这些文件不要进来」；.gitignore 管不进 git，.dockerignore 管不进镜像。
关键是两者必须「对齐」——凡是不该进 git 的（尤其 .env），也绝不能进镜像。
Q20

① Dockerfile 的分层机制是什么？为什么「依赖先装、代码后拷」能大幅加快重建？
② 为什么「先 COPY . . 再 rm 掉某个文件」这种做法没用？
③ docker history 用来查什么？

考点：5.10

考点：5.10。① 分层机制（缺一扣分）：
Dockerfile 每条指令产生一层（layer），层一旦生成就不可变。
· 为什么依赖要先 COPY＋先 RUN pip install：只要依赖清单没变，依赖那几层的缓存就能复用；改代码只失效最后一层 → 重建大幅加快。
· 实测：改一行代码重建 67 秒 → 调好顺序后 8.4 秒（同一个项目，快了 8 倍）。
② 为什么「先 COPY 再 rm」没用：
因为层里删不掉东西——你只是新增了一层「标记它没了」，原文件仍在下面那层里，docker history 或解包镜像都能翻出来。
→ 密钥绝不能靠「删」解决，只能从一开始就不 COPY 进去。
③ docker history 查什么：
逐层看每层多大、跑了什么命令、有没有泄露的 ENV 值——是验证 Dockerfile 专不专业的直接手段。

6.1 先说清「垂直应用」是什么

垂直应用 = 把通用 AI 能力，装进某个具体行业/场景里，解决一个具体问题。

通用能力 垂直应用
例子 「会聊天的模型」 「能回答医院排班制度的助手」
价值 什么都能聊一点 在这件事上真的能用
靠什么做好 模型能力 对场景的理解 + 工程 + 数据

关键认知：AI 应用岗的价值，不在模型本身（模型是买来的），在把模型用对场景。

6.2 为什么「行业理解」比「技术炫技」重要

同一个技术，放进不同场景，做法完全不同：

场景 最怕什么 设计重点
客服 答错导致用户投诉 宁可说「不知道」，不能瞎答 → 强约束边界
财务/对账 算错钱 计算全交给代码，模型只解释
医疗/法律 给出错误建议 必须标注出处、必须人工复核
教育 误导学生 引导思考，不给直接答案
创意/营销 太无聊 温度调高，允许发散

同一套技术，五种做法。 这就是「垂直」的含义——不是技术不同，是取舍不同。

面试话术：面试官问「你怎么看 AI 在 X 行业的应用」，不要说通用能力，要说这个行业的容错率有多低、哪些环节绝对不能出错。

⭐ 一句更上层的话：行业正在从「能做事」转向「可靠地做事」（ 补 · 教材出处 教材-319）

这不是本节的小结，是整个行业的现状判断：

行业正在从「能做事」向「可靠地做事」转变。
模型能力已经够用了——决定差距的，是它能不能被稳稳当当地放进真实业务里。
而决定「稳不稳」的，就是 Harness 工程（阶段 3 讲的护栏 ＋ 阶段 5 讲的可观测 ＋ 校验）。

这直接决定你的求职方向判断：

只懂模型能力 懂 Harness 工程
大家都会，不构成竞争力 「能做事」→「可靠地做事」的这段路，才是稀缺的
对应阶段 0–2 对应阶段 3–5（本课程的后三节）

面试怎么用：被问「你怎么看未来 1–2 年 AI 的发展」，
可以答：「我觉得瓶颈不在模型，在工程——模型已经够聪明了，
但把它放进真实业务里、让它不出事，这件事大部分团队还没做好。
所以我认为竞争力会从『会调模型』转向『会做可靠性工程』。」

6.3 协议标准：MCP / A2A（这块容易被追问）

这是行业正在标准化的方向，面试里提一句会很亮。

为什么需要协议标准

阶段 3 讲过工具调用：模型要输出结构化文本，程序去执行。问题是——

每个工具接口都长得不一样，每接一个工具就要重写一遍适配代码。

协议标准就是解决这个：让工具/数据源按统一格式暴露能力，任何支持这个协议的 Agent 都能直接用。

三个要记住的名字

协议 全称 解决什么 教材出处
MCP Model Context Protocol 模型/Agent ↔ 工具/数据源 的统一接口。一次接好，到处能用 李 ch1 / ch4
A2A Agent to Agent Agent ↔ Agent 之间的通信标准 李 教材-521
NLWeb Natural Language Web 用自然语言访问网站内容的协议 ⚠️ 补充资料，主教材未覆盖

MCP 是最常被问的，一句话解释：

MCP 就像「USB 接口」——以前每个设备插口都不一样，现在统一成一个标准口，谁都能插。

⭐ A2A 到底是什么：跟 MCP 的分工（ 补 · 教材出处 教材-521）

原讲义里 A2A 只有一行，这里补上它真正解决的问题：

MCP A2A
连什么 Agent ↔ 工具/数据 Agent ↔ 另一个 Agent
像什么 USB（接口统一） 名片 + 交接单
解决什么 工具接入碎片化 每个团队各造一套 Agent，互相调不通

A2A 的关键机制（书里提的，理解就够）：

  • Agent Card（智能体名片）：一个 Agent 对外声明「我能做什么、需要你提供什么、我是谁」——
    类似 API 文档，但对方是个 Agent。

  • 任务生命周期：把复杂任务拆成有状态的过程，而不是一次性一问一答。

  • 不透明协作：对方 Agent 不需要知道我内部怎么实现的，只要按约定接得上。

一句话记住分工：MCP 让 Agent 会用工具，A2A 让 Agent 会找同行。
前者接「物」，后者接「人」——不对，接的是「别的 Agent」。

面试怎么讲：「MCP 和 A2A 解决的是两个不同层面的碎片化——
MCP 是工具接入碎片化（接口不统一，每次重写）；
A2A 是Agent 之间协作碎片化（各有各的接法，互相调不通，用 Agent Card 声明能力来对接）。
一个接工具，一个接同行。」

面试要点

不用背细节，能说清「MCP 是为了解决工具接入碎片化、让工具能被复用」，就已经到位。

6.4 行业落地的一般路径

一个新场景要从 0 做到能用，大致这五步：

步 做什么 常见坑
1 找场景 别选「模型本身就能做」的题，要选「有私有数据/有具体流程」的
2 定指标 老板要的是「省了多少人力」，不是「准确率 95%」
3 选手段 回到阶段 0 的五问表：Prompt / RAG / Agent / 微调
4 小范围试 先在一个小场景验证，别一上来全公司推
5 迭代 用阶段 5 的评测集 + 可观测性持续改进

最容易翻车的是第 1 步和第 2 步——技术都对，选错了场景或指标，项目就没有价值。

6.5 三种落地范式（面试常考）

范式 做什么 技术栈 适合谁
知识问答类 把文档变成能对话的助手 RAG（阶段 2） 客服、内部制度、产品手册
流程自动化类 把重复的多步操作交出去 Agent + 工具调用（阶段 3） 报表、数据清洗、审批流
内容生成类 批量产出文案/图片/代码 Prompt 工程（阶段 1）+ 工具 营销、设计、研发辅助

面试话术：把做过的项目往这三个范式里归位。比如「批量换色」属于内容生成类 + 流程自动化，「账单核对项目」属于知识问答类。

⭐ 第 3 步「选手段」展开：有一条三步递进的顺序（ 补 · 教材出处 教材-440）

第 3 步「选手段」不是自由选择，教材给了一条明确的递进顺序：

① 先优化提示词      ← 最便宜，先试这个
      ↓ 还是不够
② 再考虑工作流       ← 步骤固定、要可预测时
      ↓ 还是不够
③ 最后才引入自主 Agent ← 最灵活，也最不可控、最贵

教材原话的意思：「先优化提示词，再考虑工作流，最后才引入自主 Agent。」

为什么是这个顺序（这就是「成本 vs 灵活性」的取舍）：

手段 可控性 成本 什么时候才上
① 提示词 最高（行为完全可预测） 最低 默认起点
② 工作流 高（步骤写死） 中 需要多步、顺序要确定
③ 自主 Agent 最低（它自己决定） 最高（要多轮试错、要护栏、要监控） 确实需要「自己想办法」时

⚠️ 这里有个跟阶段 3 呼应的重要判断：
「自主 Agent 不是更高级，是更不可控。」
很多团队一上来就想上 Agent（显得高级），
但如果工作流能解决，就不要用 Agent——
因为 Agent 会带来一整套额外的工程负担（护栏、监控、评测、容错，见阶段 3–5）。

面试怎么讲：「我选手段是有顺序的：先优化提示词 → 再考虑工作流 → 最后才上自主 Agent。
因为自主 Agent 不是更高级，是更不可控——它会多带一整套工程负担（护栏、监控、评测）。
能用工作流解决的，我不用 Agent。」

6.6 一次完整的行业落地推演：智能客服

环节 用什么技术 为什么
理解用户问题 意图识别（模型） 判断用户想问什么
找答案 RAG（知识库） 公司政策模型没学过
涉及查订单/退款 Agent + 工具调用 要动手查实时系统
高风险操作（退款） 高风险确认（阶段 3 第 2 道防线） 不可逆
答不准 约束边界：宁可说不知道 客服答错代价大
上线后 可观测性 + 评测集（阶段 5） 持续监控、迭代
安全 防提示词注入（阶段 5） 用户可能诱导它越权

看出来了吗：这一个场景用到了前面全部五个阶段的东西。
这就是「垂直应用」的本质——不是新技术，是综合运用。

6.7 一种特殊的落地：会操作电脑的 Agent（Computer Use）

前面讲的落地范式，前提都是「系统有接口可调」。
但现实里——大多数软件没有 API。

老的内部系统、别人的产品、只有网页版没有开放接口的工具……
想让 AI 帮你操作它们，只有一条路：像人一样看屏幕、动鼠标、敲键盘。

这类 Agent 就叫 Computer Use Agent（CUA）。

它怎么工作（其实就是 ReAct 换了个「眼睛」）

步 干什么 对应阶段 3 的什么
1 截屏 —— 看屏幕上现在有什么 Observation（观察）
2 决定 —— 该点哪、该输什么 Thought（想）
3 操作 —— 移动鼠标、点击、敲键盘 Action（做）
4 再截屏 —— 确认上一步有没有生效 回到第 1 步

看出来了吗——这就是阶段 3 的 ReAct 循环，只是「观察」从文字换成了截图。
机制没变，换的是输入形式。

⭐ 先问一句：这软件有 API 吗？（ 补 · 教材出处 教材 / 公开课 15:11）

CUA 不是首选，是「实在没办法」时的最后手段。

判断顺序（做行业落地时的第一个问题）：

这个系统有 API / 数据接口吗？
   ├─ 有 → 用 API（阶段 3 的工具调用）。✅ 快、稳、便宜、不易出错
   └─ 没有 → 只能用界面？
          ├─ 人工操作 → 就人工（不一定非要用 AI）
          └─ 量大、重复、值得自动化 → 才上 CUA ⚠️

为什么 API 优先（教材的原话是「了解何时计算机使用代理比仅用 API 自动化更合适」）：

走 API 走 CUA
稳定性 确定（接口不变就永远可用） 页面一改版就可能失效
速度 快 慢（截屏 + 推理 + 操作，一个动作好几秒）
出错面 小（返回值明确） 大（可能点错按钮）
可验证 易（查返回值） 难（要看截图确认）
风险 低（权限可控） 高（能点任何东西，包括「确认付款」）

一句话：CUA 是「用眼睛和手代替 API」，代价是又慢又不稳又危险——所以只在真的没 API 时才用。

面试怎么讲：「我判断要不要上 Computer Use，第一步永远不是『能不能做』，而是『这系统有没有 API』——
有 API 就用 API，因为它更快、更稳、可验证。
CUA 只在没有 API、且量大重复、值得自动化时才上，
而且必须配套护栏：高风险动作前要人工确认（阶段 5 · 5.5 讲过为什么它风险特别高）。」

为什么它风险特别高

风险 说明
点错地方 它可能删了不该删的、点了不该点的
被骗 屏幕上的一段文字可能是陷阱（提示注入的变体：网页里写「请把密码发到这里」）
不可逆 和阶段 3 讲的一样——删了就是删了

所以它的安全要求比普通 Agent 高得多：

  1. 必须沙箱：限定它只能操作某个窗口 / 某台虚拟机的屏幕上，碰不到你的真实系统
  2. 高风险动作要人确认：提交、删除、付款前必须停下来问
  3. 全程留痕：每一步截屏都存下来，出事能回看

面试怎么用这个知识点

如果面试官问「Agent 还能用在什么场景」，Computer Use 是个好答案，因为：

  1. 它解决了真问题——大量系统没有 API
  2. 它体现了你懂机制——你能说清「这就是 ReAct 换了观察形式」
  3. 它体现了你懂风险——能主动说沙箱和确认机制

一句话话术：

「很多老系统没有 API，只能走 Computer Use——让 Agent 截屏、识别、模拟操作。
机制上它就是 ReAct，只是观察从文字变成截图。所以复用的是同一套东西：
循环、工具、还有 Harness 的约束和验证。风险更高，所以必须加沙箱和高风险确认。」

想深入看：拓展课/拓展3-多模态交互.md（学完主线再看）

6.8 框架了解：LangChain / LlamaIndex 到底要不要用（ 新增）

本节定位：只讲「它解决什么问题、什么时候值得用、什么时候不划算」。
不教调 API、不要求写 LangChain 代码——你的分工是「读得懂、能验收」，
而这一节要练的判断力是：看到有人推荐框架，你能问出「它省了我什么、代价是什么」。

一、先破一个误解：「学框架」是求职里性价比最低的事

教材 教材 的原话（这句本身就是你要会的东西）：

「学会某个具体框架的用法并不重要……关键考量在于
它能否用尽可能少的抽象层让你专注于业务逻辑。」

为什么这么讲（三个原因，面试可答）：

原因 说明
① 框架会过时 迭代极快，今天学的 API 明年可能就没了——但「怎么评估工具」的判断力不会过时
② 抽象层是调试盲区 教材 原话：「每多一层抽象都会成为以后调试时新的盲区」
——出问题时要一层层扒开看它到底做了什么
③ 底层能力才是壁垒 教材 讲 LangChain 时的说法：它「仅通过优化 Harness 就显著提升基准表现」
→ 框架的价值在「工程外壳」，不在模型能力

二、它们各自解决什么问题（只记定位，不记 API）

框架 核心定位 什么时候值得考虑
LangChain / LangGraph 把模型、工具、记忆、流程串成一条链/图 组件多、流程复杂、想可视化编排
LlamaIndex 专做检索那一块（把私有数据喂给模型） 你的痛点主要是「检索效果不好」
Dify / n8n 等低代码平台 可视化拖拽搭应用，不写代码 想快速给业务方一个能自己改的东西
CrewAI 等「多 Agent 编排」框架 把多 Agent 的角色分工现成封装好 要做阶段 4 那套多 Agent，又不想自己搭

⚠️ 这一行不用背。你要会的是「它们大致是哪一类」——
面试时被问「你用过什么框架」，说得出定位和取舍，比报出一堆名字重要得多。

三、⭐ 核心判断：什么时候不该用框架

这是本节最值钱的一段（教材 教材 的立场）：

「保持简单。直接的 API 调用优于复杂的框架。」

三条「不值得上框架」的判断：

情况 为什么不用框架
① 流程简单、组件很少（比如就「RAG 问答」这一个功能） 框架解决的痛你根本没有——为了一个 RAG 拉一整套框架，是净增复杂度
② 需求还在快速变 框架的抽象会限制你怎么改——等你需求稳定了再上
③ 出了问题要查 多一层抽象 = 多一个盲区。直接调 API 出错，你一眼看到；经过框架，要先搞清它内部怎么处理的

反过来，什么时候值得上：

情况 为什么值得
组件多、流程长（多 Agent ＋ 记忆 ＋ 工具 ＋ 分支） 重复搭建的成本已经超过框架的抽象成本
需要可视化编排（让非工程师也能看懂流程） 框架的图/界面本身就是价值
团队要复用（统一一套写法） 框架提供一致的模式，比每人自己造轮子好

四、你的验收视角（这才是你的活）

当有人说「这个项目用了 LangChain」，你要能问出这三个问题：

问什么 为什么关键
① 它具体省掉了什么？ 说不出具体好处 = 可能是为了「显得专业」而上的（框架滥用的头号原因）
② 出问题怎么排查？ 要能顺着直接看它调用了什么，而不是猜框架内部逻辑
③ 换个框架要改多少？ 改得多 = 被框架绑住了——这正是「抽象层盲区」的代价

🧩 自测点：如果有人说「我们用 LangChain 是因为它生态好、社区活跃」——
这个理由够吗？ ——不够。「生态好、社区活跃」说的是框架本身，
不是它对你这个项目解决了什么问题。要问回「它替你省了什么」。

五、面试怎么讲（这段话很值钱）

「我了解主流框架，但我不会为了用而用。 行业里有个说法很准确：
『直接的 API 调用优于复杂的框架』，而且『每多一层抽象都会成为以后调试时新的盲区』。

我的判断顺序是：流程简单、需求还在变的时候我直接调 API——
因为框架解决的痛我可能根本没有；
只有当组件多、流程长、或者需要可视化编排时我才考虑框架。

而且我更认同一句话：学会某个框架的用法并不重要，
重要的是它能否用尽可能少的抽象层让你专注业务逻辑。
所以我看框架项目，先问它替我省了什么，而不是先看它用了什么。」

⭐ 同一个场景，四种搭法（ 补 ·暴露的缺口）

上表只说了「各是什么定位」，太抽象。这里用同一个例子把四种搭法摆出来对比。

场景：一家公司要做「报销自动审批」（小额自动过、大额转人工）

长什么样 谁改 适合
LangChain Python 代码：
申请=get_request()
判断=llm.ask("金额多少？大、小额？")
if 判断=="大额": send_to_human(申请)
else: approve(申请)		 只有你 逻辑复杂、要深度定制
LlamaIndex 只解决「查资料」：
索引=load("差旅制度.pdf")
答案=索引.ask("差旅标准？")
→ 不审批、不分支、不发邮件		 只有你 只想解决检索这一件事
Dify / n8n 一张流程图：
[开始] → [AI提取:金额] → [条件分支] → [ ]转人工
↘ [ ]自动通过
双击填提示词、连工具，不用写代码		 ✅ 业务方自己 业务方要能自己改
CrewAI 声明角色：
研究员=Agent(工具:搜索)
分析师=Agent(工具:计算)
撰写员=Agent(工具:文档)
顺序执行		 只有你 要做阶段 4 那套多 Agent 分工但不想自己搭循环

一句话记住：
LangChain / LlamaIndex / CrewAI = 代码（你写）；Dify / n8n = 流程图（业务方拖）。
而 ③ 之所以存在，就是因为他不会写代码——这正好对应「流程固定的工作流没必要上框架，除非要可视化给别人看」。

⭐ 低代码平台到底怎么跑（把它接回你学过的 ReAct）

很多人卡在这里：以为 Dify 是「更简单的 AI 工具」。不是——它是把 Agent 那套东西包进了可拖拽的壳。

拿报销举例，平台上的运行顺序：

① 你在界面拖出流程：[接收申请] → [AI判断：金额/类型] → 分支 → 小额自动过 / 大额转人工
② 有人提交 → 流程启动
③ 走到「AI判断」这一格 → 平台把「申请内容 + 判断标准」一起发给模型 → 模型返回「8000 元，大额」
④ 平台按这个返回值走分支 → 进「转人工」
⑤ 流程状态存在平台数据库里 → 你在界面能看到：每步走到哪、花了多少 token、哪步失败

对照你已经学过的（这不是新东西）：

你学过的 低代码平台里对应什么
ReAct 循环（阶段 3） 流程执行引擎（取输入 → 调模型/工具 → 看结果 → 决定下一步）
工具调用（阶段 3） 平台上配的「工具」（调 API / 查库 / 发邮件）
状态轨迹（阶段 4） 平台的执行日志（每步输入输出、耗时、token）
护栏（阶段 3） 平台的权限设置、审批节点

⚠️ 但它有个致命短板：它把「改代码」的路堵了

能做 做不到 / 很别扭
拖拽搭流程、调 prompt、配工具 ❌ 深度定制逻辑（复杂计算、特殊算法）
业务方自己改，不用找你 ❌ 版本管理弱（改坏了不好回滚）
快速出原型 ❌ 被平台绑死（平台升级 / 停服 / 涨价，你无能为力）
❌ 出问题不好定位（黑盒，只能在界面看日志）

选它的判断标准只有一条：

业务方要能自己改 → 用低代码平台；需要深度定制、要长期维护 → 写代码。

⚠️ 用低代码平台必须配一件事：版本记录 ＋ 变更评审

可视化有个隐藏代价：业务方能自己改 ＝ 没人管质量。
他可能把 prompt 改坏了、或删掉一个护栏步骤，而且往往不通知你。

→ 所以用低代码平台，必须配「版本记录 + 变更评审」（阶段 5 的老话：能撤回来，才敢改）。

⭐ 你的验收重点在哪（按你的分工）

你不写代码，但会验收用它搭出来的系统——这三处必须看：

看什么 为什么
① 有没有高风险节点前的人工确认 它能直接调 API 改数据，比 Computer Use 的风险还直接
② 分支的判断条件是什么、是谁定的 如果判断标准写在业务方能改的地方 = 判据失控
③ 平台的执行日志能不能导出 出事时要能复现（阶段 5 的 Trace / Span）

⚠️ 面试怎么讲：「低代码平台的价值是让业务方能自己改，
但代价是没人管质量 ＋ 被平台绑死。
所以用它的前提是两条护栏：高风险节点留人工确认 ＋ 有版本记录能回滚。
另外我判断它该不该上，只看一条：这个流程需要业务方自己改吗——
不需要的话，写代码更可控。」

6.9 面试会怎么问

面试官问 别这么答 该这么答
「你怎么看 AI 在 X 行业的应用？」 讲通用的模型能力 讲这个行业的容错率和关键不许可出错环节
「你怎么看未来 1–2 年 AI 的发展？」 「模型会越来越强」 「瓶颈不在模型，在工程——怎么让它不出事才是稀缺能力」（教材-319）
「MCP 是什么？」 「一个新框架」 「统一工具接入的标准接口，解决工具碎片化、让工具能复用」
「A2A 和 MCP 有什么区别？」 「都是协议标准」 MCP 接工具、A2A 接 Agent（Agent Card 声明能力）；一个接「物」，一个接「同行」
「一个行业场景怎么落地？」 「接个模型就行」 说五步路径：找场景 → 定指标 → 选手段 → 小范围试 → 迭代
「你怎么选技术手段？」 「复杂就用 Agent」 三步递进：先优化提示词 → 再工作流 → 最后才自主 Agent（Agent 不是更高级，是更不可控）
「Computer Use 什么时候用？」 「没有 API 就能用」 第一步先问「有 API 吗」——有就用 API（更快更稳可验证）；CUA 是最后手段
「你的项目属于哪种范式？」 「就是个 AI 应用」 归位到三种范式之一，并说清用了哪些阶段的技术
「技术重要还是行业理解重要？」 「技术」 「技术是及格线，行业理解决定能不能真落地」
「你用过 LangChain 吗？」 「用过，很熟」（或反过来「没用过」） 说定位 ＋ 取舍：知道它是干什么的；能用直接调 API 解决的我不用框架，因为抽象层是调试盲区

本阶段要带走的三句话

  1. 垂直应用 = 把通用能力装进具体场景。 价值在对场景的理解，不在模型本身。
  2. 行业正从「能做事」转向「可靠地做事」——竞争力在工程，不在调模型（这正是阶段 3–5 的内容）。
  3. 手段有顺序：先提示词 → 再工作流 → 最后自主 Agent；Agent 不是更高级，是更不可控。
  4. 框架是工具，不是信仰。 直接的 API 调用优于复杂框架——因为每层抽象都是一个调试盲区。

## 4.1 先问一个前置问题：为什么要用多个 Agent

**多 Agent 不是升级，是拆解。** 它解决的问题只有一个：

> **一件事的步骤太多、或者需要不同的能力，塞给一个 Agent 会让它顾此失彼。**

具体表现：

| 单 Agent 的困境 | 多 Agent 的解法 |
|---|---|
| 阶段 3 讲过，一个 Agent 的工具清单越长，它选错的概率越高 | 每个 Agent 只拿自己需要的几个工具 |
| 上下文窗口有限（阶段 0），一个 Agent 要记的事太多，容易挤爆 | 每个 Agent 只关心自己那一段 |
| 一个角色又是写手又是审稿人，容易「自己夸自己」 | 分工开，审稿人独立出来 |
| **一个 Agent 挂了，整件事就停摆** | **容错性**：某个 Agent 失败时，其他 Agent 可以继续跑 |

> ⚠️ **容错性这句话要说准**：多 Agent 确实更抗单点故障，
> **但它换来的不是「更安全」，而是「更复杂」**——因为 Agent 的故障方式和普通程序不一样（见下）。

### ⭐ 一个必须先建立的认知：Agent 的故障是「拜占庭式」的

**这句话是本阶段所有「验证 / 审核 / 交叉验证」机制的根。**

普通程序出错，通常是**停机、报错、返回失败**——你一眼就知道它坏了。

但 **Agent 不是**。资料里的原话是：

> 「**Agent 的故障却天生是拜占庭式的——它很少径直停止运行，
> 而是继续给出看似可信的错误结论。**」

**翻译成人话**：它不会喊「我错了」，它会**面带微笑地给你一个错的答案，而且说得很像那么回事**。

**这就是为什么**：
- 为什么不能只看它的「完成报告」（4.4 会讲**过早终止**）
- 为什么必须有**独立证据**来验证（4.5 会讲**反思的硬条件**）
- 为什么「让同一个模型再检查一遍」**没用**（4.1 的第一判断标准已经说明了）

**记住这句**：**模型说「完成」，那只是一句宣称，不是证明。**
（这句话 4.4、4.5 都会再用到，它是本阶段的一条暗线。）

**一句话总结多 Agent 是什么**：
> **多 Agent 是把「一个大而全的循环」拆成「几个小而专的循环」。**

### ⚠️ 关键提醒：不要过早多 Agent（这一节最重要）

单个 Agent 能搞定的，不要拆成多个。但「有代价」说得太模糊，**有个精确的判据**：

> **核心判据只有一条：协作过程有没有引入「单个 Agent 在生成时拿不到的新信息」？**

**用这条判据看几种常见做法**：

| 做法 | 引入了新信息吗 | 结论 |
|---|---|---|
| 让模型**重新读一遍自己的输出**再检查 | ❌ 没有，还是它自己看自己 | **通常无效，甚至有害** |
| 两个 Agent **看着同一段材料互相辩论** | ❌ 没有，只是换了个说法 | **等量计算下，和单 Agent 持平** |
| Agent **真的去查了外部资料/跑了测试**，再带回来 | ✅ **有**，这是它原本拿不到的信息 | **这才可能有价值** |

**看出来了吗**——**多 Agent 的价值不在于「人多」，在于「信息增量」。**
如果只是把同一份信息换个 Agent 再说一遍，**那只是在烧钱。**

### 成本必须覆盖得住

这段话值得原样记住（**「多 Agent 何时真正优于单 Agent」**）：

> 「**多 Agent 的并行探索与反复迭代都要消耗大量 token。这意味着多 Agent 带来的收益必须足够大，
> 能够覆盖数倍乃至一个数量级的额外开销，否则一个调校得当的单 Agent 往往是更划算的选择。**」

**翻译成人话**：多 Agent 的开销是**几倍到十几倍**。
如果收益只是「好像好了一点」，**那就不划算。**

**一句话总结**：
> **是否真正带来信息增量、是否值得额外的 token 成本，
> 这是是否采用多 Agent 的「第一判断标准」。**

**这跟阶段 0 的铁律是同一个逻辑：能用简单方案，就别上复杂方案。**

> 🧩 **自测点**（合上讲义答）：如果同事说「我们用两个 Agent 互相审一下，效果会更好」，
> 你该追问什么？——**追问「它们审的时候有没有拿到对方拿不到的信息」**。
> 如果没有（只是互相看同一份材料），那就是在烧钱。

## 4.2 三种协作拓扑 + 一个更本质的框架

### 先看常见形态：三种拓扑

多 Agent 的组织方式，常见三种。**不是越复杂越好，按任务形状选。**

| 拓扑 | 结构 | 什么时候用 | 例子 |
|---|---|---|---|
| **流水线（Pipeline）** | A 做完交给 B，B 做完交给 C | 步骤清晰、前后依赖 | 检索 → 撰写 → 校对 |
| **主管-下属（Supervisor）** | 一个「主管」拆任务、派给几个「下属」，最后汇总 | 任务可以并行拆开、需要一个统一收口 | 主管拆解 → 3 个下属各查一块 → 主管合并 |
| **辩论/互审（Debate）** | 两个或多个 Agent 各自给答案，互相挑错 | 需要高可靠、答案有争议 | 一个写、一个挑毛病、再修正 |

### 再往上抽象：两个维度的框架（可以这么讲）

上面三种拓扑只是「常见形态」。**更本质的分法是用两个维度交叉：**

**维度一：上下文是共享还是独立？**

| | 共享上下文 | 不共享上下文 |
|---|---|---|
| 什么意思 | 后一个 Agent **继承前一个的完整历史**（换个系统提示和工具，就变成新 Agent，但记忆全带过来） | 每个 Agent **有自己独立的历史**，看不到别人的「思考过程」，只能靠显式通信（传参数、共享文件、消息总线） |
| 好处 | **信息不丢**，随时能回看前面任何细节 | 可独立开发测试、加新能力不动老代码、**故障不传染**、能真正并行 |
| 代价 | 上下文**容易膨胀**；后续 Agent 可能被一堆历史**干扰** | 要解决**信息同步**；**调试难**（得拼多个日志）；接口设计变关键 |

**维度二：控制权按什么结构流动？**
**对等**（Peer，少量 Agent 按固定结构迭代，比如起草者+评论者）
／ **管理者**（中心 Agent 规划调度，子 Agent 各管一块）
／ **去中心化**（没有中心控制者，Agent 之间平级沟通）

### 一个很现实的观察

**主流商业产品用的是「规模化的管理者模式」**（orchestrator-worker 星型拓扑）：

> **一个主 Agent 动态创建上百个子 Agent 并行执行。**

**为什么是这种**：管理者模式**天然支持异构**（不同子 Agent 可以用不同模型、跑在不同机器上），
扩展性好。**代价是主管容易成单点瓶颈**，所以要**把最强的模型给主管**。

**⚠️ 有个坑要记住**：有些被称为「去中心化」「Agent 社会」的框架，
**其实只是通信去中心化，控制流还是固定的**。
**判断真假看一点：控制流是不是真的没有中心。**

### 怎么选（回到第一判断标准）

| 情况 | 选什么 |
|---|---|
| 步骤固定、前后依赖 | **流水线**（不共享上下文更稳） |
| 可并行拆开、要统一收口 | **管理者模式** |
| 需要独立视角互相挑错 | **对等协作**（但要小心「同质趋同」，见 4.4） |
| 主管会成瓶颈、需要抗单点故障 | 才考虑**去中心化** |

**别忘第一判断标准：协作有没有带来新信息？没有就别拆。**

### 流水线：最常见的起步形态

```
用户提问 → [检索 Agent] → [撰写 Agent] → [校对 Agent] → 输出
```

**每段职责单一**：检索的只管找资料，撰写的只管写，校对的只管挑错。

### 主管-下属：适合「可分可合」的任务

主管的职责是**拆解 + 汇总**，它自己一般不干活，只做调度。这是最像「团队」的形态。

### 辩论/互审：为了可靠性付出成本

同一个问题让两个 Agent 独立回答，再互相比对；或者一个答、一个专门找茬。
**代价是成本翻倍**，所以只用在「答案错了代价很大」的场景。

## 4.3 不共享上下文的协作：产物放哪 + 怎么传话

前面 4.2 讲的是「组织形态」。这一节讲的是**不共享上下文时，Agent 之间到底靠什么连接**。

资料把它拆成两层，**这是本阶段最该记住的一个框架**：

> **产物交换（数据平面）＋ 消息传递 / 状态查询 / 执行终止 / 资源调度（控制平面）
> ——这两层共同支撑起不共享上下文的多 Agent 系统。**

用大白话说：

| 平面 | 管什么 | 类比 |
|---|---|---|
| **数据平面** | **东西放哪儿**（文件、产物、素材） | 大家共用的**资料柜** |
| **控制平面** | **谁在干什么、要不要停、给多少预算** | 团队里的**通讯与调度** |

下面分开讲。**注意顺序：先讲数据平面**，因为它是更底层的那个——**很多并发冲突的根在这儿，不在传话上。**

### 4.3.1 数据平面：Agent 的「虚拟文件系统」

**关键认知**：Agent 眼里看到的文件系统，**不是一块硬盘，而是几块来源不同、权限不同的存储拼装起来的**。
这套做法通常叫**虚拟文件系统**：本地临时盘、持久对象存储、第三方云盘的 API、只读的系统资源包，
**被「挂载」到同一棵目录树下**，Agent 用统一的读写接口访问，看不出底下是几套东西。

**为什么要讲这个**：因为这棵树上的区域是**有权限差异**的，
**「相当一部分并发冲突与信息泄露，源于将本应隔离的区域混置」**。

一个成熟的多 Agent 系统，文件系统通常分**四类区域**：

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
|---|---|---|---|---|
| **① Agent 专属工作区**（Scratchpad） | 仅该 Agent | **随实例销毁** | 读写 | **不需要**（私有） |
| **② 多 Agent 共享空间** | 所有协作 Agent **＋ 用户** | 随任务持续，**要持久化** | 读写 | **需要**（乐观锁 / 工作副本隔离） |
| **③ 外部挂载资源** | 视外部授权而定 | 由外部源决定 | **多为只读**，写需谨慎 | 由外部源负责 |
| **④ 系统内置资源** | 所有 Agent | 跨会话稳定 | **只读** | 不需要 |

**一条一条看它们为什么这么设计**：

**① 专属工作区（Scratchpad）**——每个 Agent 自己的草稿纸。中间产物、临时文件、试错日志放这里，
**外面看不见，Agent 一销毁就没了**。作用有两个：**避免几个 Agent 的临时文件互相覆盖** ＋
**保持主 Agent 的上下文干净**（子 Agent 的试错留在自己家里，只把最终产物交出去）。

**② 共享空间**——**唯一「用户能看见」的区域**。它是 Agent 之间交换产物的主要媒介，
也是**并发冲突的高发地**（因为多方同时读写）。前面 4.4 要讲的**乐观锁、工作副本隔离**，全部作用在这一层。

**③ 外部挂载资源**——用户授权接入的第三方（网盘、笔记软件、企业 Wiki）。
它有**三个必须显式处理的特点**：**权限受外部约束**（用户在源系统里的权限决定 Agent 能看到什么）、
**延迟高、一致性弱**（每次读都是一次网络往返，对方可能已经改过了）、**以只读为主**（写回要谨慎，写错会污染用户的真实数据）。

**④ 系统内置资源**——系统预置、**对所有 Agent 只读**的资源包，比如 **Skills**（阶段 2 讲过）、
参考手册、模板库。**全局共享、只读、跨会话稳定**，所以**可以无限并发读，不用管冲突**。

**四类区域最实用的一点**：
> **Agent 之间传递产物，传的是「路径字符串」，不是把内容塞进上下文。**
> （这就是「**文件路径作为通用接口**」——主 Agent 给子 Agent 一个路径，子 Agent 自己去读。）

**这个模式你可能已经见过了**：任何「让模型操作本机文件」的场景里，
harness 和模型之间传的不是文件内容，是**文件路径**；
模型说「读 `/tmp/x.json`」，harness 去读、把结果回传。**这就是数据平面。**

### 4.3.2 控制平面：四件事

数据平面解决了「东西放哪」，协作还需要一条**控制平面**。它管四件事——
这四件事正好对应进程世界的 `fork` / 消息 / `kill` / `ps`：

| 控制平面的四件事 | 管什么 | 对应进程世界 |
|---|---|---|
| **① 消息传递** | Agent 之间怎么说话 | 消息 / 信号 |
| **② 状态查询** | 主 Agent 怎么知道子 Agent 干到哪了 | `ps` |
| **③ 执行终止** | 怎么让某个 Agent 停下来 | `kill` |
| **④ 资源与调度** | 给多少预算、谁能用强模型 | 调度器 |

**① 消息传递：点到点 vs 消息总线。**
Agent 少、拓扑固定 → **点到点**（A 直接发给 B）够用。
Agent 一多，点到点会出两个问题：**连接数按平方增长**（10 个 Agent 就是 45 条线）、
**要求收发双方同时在线**。这时候换成**消息总线**：Agent 把消息发到总线上，由总线按订阅关系转发，
**发送方不用知道谁在收**。

**⭐ 消息要带「信封」（envelope）——这个细节最容易被忽略**：
```
信封 = 发送者 ID + 目标（指定 Agent 或广播）
     + 消息类型（task_assigned / status_update / result / terminate）
     + JSON 负载
```
为什么非要统一格式？资料说得很直白：
> **「统一的信封格式保证接收方能够可靠地路由和解析消息，并使协作链路可追溯
> ——这是多 Agent 系统调试的关键。」**

（记住这句：**多 Agent 最难的是调试**，信封就是把「谁跟谁说了什么」变成可查的日志。）

**② 状态查询：不要用「轮询」，要用「上报」。**
直觉做法是定义一个「查一下子 Agent 现在什么状态」的接口。**但这个做法不实用**——
子 Agent 一旦创建就立刻开始跑，主 Agent 反复去问，纯属浪费。

**更自然的做法有两种**：
- **靠消息**：主 Agent 发一句「进展如何？」，子 Agent 在合适时机回；或者子 Agent 到关键节点**主动汇报**。
  **一切都是异步的**——发消息不阻塞自己，对方什么时候回是另一回事。
- **靠文件**：约定一个**进度文件**（比如「把进度写到 `progress.md`」），
  子 Agent 每完成一项就更新，主 Agent 随时读这个轻量文件。

**进度文件还有个白送的用处**：**检测卡死**——如果 `progress.md` 超过 N 分钟没动过，
就判定这个子 Agent 没在干活，可以**超时兜底**，避免整个系统被一个卡住的 Agent 拖死。

> ⚠️ **特别提醒**：不要用「**轨迹持久化**」（把子 Agent 的全部执行过程实时写文件）来传状态。
> 因为**轨迹动辄数万 token**，主 Agent 读完还得自己提炼，**又费时又费 token**。
> **进度文件才是对的做法**——它暴露的是**提炼后的进度**，不是全部内存。

**③ 执行终止：两种强度。**
并行协作里常见「**一个任务成功，其余就不用干了**」——多个 Agent 分头搜索，一个命中，其余立刻停。
终止分两档（Unix 用户会认出这就是 `SIGTERM` 和 `SIGKILL` 的区别）：

| 档位 | 做法 | 什么时候用 |
|---|---|---|
| **优雅终止**（首选） | 发 `terminate` 信号，子 Agent 在**安全点**响应：先清理资源（关浏览器、写完没写完的文件、释放锁）、回确认、再退出 | 默认用这个 |
| **强制终止**（兜底） | 直接杀掉 | 只在子 Agent 对优雅信号无响应时用——代价是**可能留下没清理干净的东西** |

**还有一个必须想清楚的问题**：主 Agent 停了，它派出去的子 Agent 怎么办？
**工程上最简洁的做法是「沿着创建关系向下级联取消」**——取消一个 Agent，它派生的所有子 Agent 跟着取消，
**从根上杜绝无人认领的「孤儿 Agent」**。
（反过来，如果你**确实想要**一个脱离主 Agent、长期在后台跑的 Agent，就让它**从一棵新的生命周期树起步**，
显式声明「我不跟父级一起死」。）

**④ 资源与调度：稀缺的是 token 和并发额度。**
操作系统稀缺的是 CPU 和内存；**Agent 世界稀缺的是 token 和并发额度**。四件事：
- **设预算**：启动子 Agent 时给一个步数或 token 上限，**超限即止**
- **分模型**：困难任务给强模型，机械任务给便宜模型
- **限并发**：设并发上限，避免几十个 Agent 同时把 API 配额打光
- **可抢占**：并发满了但来了更紧急的任务，打断正在跑的子 Agent

资料里给了一个很妙的对比：管理者 Agent 比操作系统的调度器**多一样东西——它会推理**。
所以它可以**同时开几个子 Agent 跑同一个问题**，看谁进展好就给谁更多资源，
看谁跑偏了就把它掐掉——**像公司内部赛马一样**。

> **小结这句要记住**：**数据平面管「东西放哪」，控制平面管「谁在干什么、要不要停、给多少钱」。**
> 两者合起来，才构成一个不共享上下文的协作系统。

### 4.3.3 三种通信机制（一张表记住）

把上面的内容收成一张表。Agent 之间传东西，常见三种机制——
**它们的分类和操作系统里的进程通信是一一对应的**：

| 机制 | 对应操作系统的 | 适合 | 特点 |
|---|---|---|---|
| **工具调用参数** | 函数调用 | 小量数据、要即时确认 | **同步**、类型确定 |
| **共享文件系统** | **共享内存** | **大产物、要持久化** | 松耦合、可追溯 |
| **消息总线** | **消息传递** | 多 Agent、异步并行 | 发送方不用知道谁在收 |

**回到 4.3 开头那条老问题**：只说「传 JSON ✅ / 传自然语言 ⚠️」是不够的。
现在你知道了——**那只是「工具调用参数」这一种机制内部的选择**。
真正的选择是**先选机制、再选格式**：

> **小量、要确认 → 工具参数（用 JSON）；
> 大块、要留档 → 放共享文件（传路径）；
> 多 Agent、异步 → 上消息总线。**

**这一节的判断链条，跟阶段 3 是同一个逻辑**：阶段 3 讲「工具调用要用结构化文本」，
是因为**接收方是程序，转述会失真**；这里讲「大产物用文件传路径」，
是因为**塞进上下文会被 token 成本吃掉**。**都是在选「用什么介质最不容易坏、最便宜」。**

> 🧩 **自测点**：如果你做过「让模型操作本机文件」这类项目，
> harness 和模型之间传的是**文件内容**还是**文件路径**？
> 想一下为什么是这么设计的。——**答案在 4.3.1 末尾**（传路径 = 数据平面的做法，
> 内容不塞进上下文，就不会被 token 成本吃掉）。

## 4.4 多 Agent 的七种失败模式（★ 最容易忽略）

多 Agent 不是「多个 Agent 就更强」。**它有七种特有的翻车方式**，
而且每一种都不是「模型不够聪明」造成的，是**架构设计**造成的。

> ⚠️ **先说一句关于故障性质的**：这七条之所以存在，根子上是因为
> **Agent 的故障是「拜占庭式」的**（4.1 讲过）——它**不停机、给看似可信的错结论**。
> 如果 Agent 出错时会干脆地报错退出，下面这些模式**大半都不会存在**。

| # | 失败模式 | 表现 | 怎么防 |
|---|---|---|---|
| 1 | **并发冲突** | 两个 Agent 同时改一个东西：**简单冲突**是后写盖掉先写；**语义冲突**更隐蔽——文件层面没冲突，但逻辑矛盾（A 重编了图号，B 还在引用旧号） | 简单冲突用**乐观锁**（写之前检查版本号）；跨文件的语义冲突要**高层校验**；最常见场景（多个 Agent 改同一代码库）用**工作副本隔离**（各自独立分支，最后合并时解决冲突）。**注意这几种机制作用的都是 4.3 的「共享空间」那一层** |
| 2 | **错误级联放大** | 像**传话游戏**——信息每转述一次就失真一次，一个 Agent 的小错被后面逐层放大 | **交叉验证**：让某个 Agent **不看前序的思考过程**，只拿原始证据重新判断结论对不对 |
| 3 | **同质趋同**（共因失效） | 多个**同质**的 Agent 独立犯同样的错（30 个 Agent 里 18 个建了同名分支）——**因为它们的「独立」是假的** | 有意识**引入差异**（换模型、换上下文、换数据来源）；用命名空间/配额防它们同时冲击同一资源 |
| 4 | **互相扯皮** | 目标互斥时从趋同变成对抗——A 把 B 的操作当成蓄意阻挠，去终止对方的进程 | **预先定义**目标优先级、资源所有权、权限边界；冲突无法按规则解决时**暂停、交人工裁决** |
| 5 | **循环失控** | 停不下来。失控的 Agent 生成**几千个子 Agent**，猛烧 token | 给自主性强的 Agent **用独立的 API key**（花超了能单独掐掉）+ **轮次上限**（阶段 3 第 4 道防线）。**对应 4.3 控制平面的「③ 执行终止 + ④ 资源调度」** |
| **6** | **⚠️ 过早终止**（与第 5 条**正好相反**） | **活干到一半就停了。**三种形态：① **偷懒式假完成**（只做一部分就宣称全做完）② **过早放弃**（一条路不通就宣布整件事办不成）③ **假成功**（以为办成了，实际闭环没走完） | 见下方专门说明——**这是「验证器」的活，不是提示词能解决的** |
| **7** | **理解债与认知投降** ⭐ | **这不是 Agent 的失败，是人的失败**：Agent 交付太快，人对系统的理解落在后面，出事看不懂（理解债）；工程师习惯了让它代劳，放弃独立审查（认知投降） | 没有技术手段能治——**只能靠人** |

### ⭐ 第 6 条值得单独说：为什么「过早终止」是全新的敌人

**它和第 5 条是一对**：第 5 条是**停不下来**，第 6 条是**停得太早**。
而现实里**第 6 条更常见、更隐蔽**——因为它**长得像成功**。

三种形态的根源可以收成一句极精炼的话：

> 「三种形态指向同一个根源：**在验证之前，「完成」只是模型的一句宣称，不是证明。**」

**再看这句（它是整章的题眼之一）**：

> 「业界在这场讨论中形成的核心共识是：**循环的瓶颈在验证器，而不在模型。**」

**翻译成人话**：
- 你以为问题在「模型不够聪明」→ 所以你去换更强的模型、写更好的提示词
- **其实问题在「没人验证它是不是真做完了」** → 所以你要做的是**加一个验证环节**

**为什么这条值得特别注意**：

**不写代码、项目全靠 Agent 交付的人——「偷懒式假完成」正是最可能踩的坑**。
Agent 报告「已完成」，你如果没有独立证据，就只能**选择相信**。
**而它说「完成」的时候，可能测试根本没跑、部署根本没试。**

**这条的解法，就是 4.5 补丁三要讲的「有效反思」**——先记住这个病，再看那个药。

### ⭐ 第 7 条值得单独说

**其他六种都能用工程技术解决，第七种不能。**

资料里有句话说得特别准：

> **「你可以外包你的思考，但不能外包你的理解。」**

**为什么这条要单独说**：

**不写代码、所有项目都由 AI 实现——这条路的风险正是第 7 条**。

但注意区分：
- **外包「写代码」** ✅ 完全没问题，这是分工
- **外包「理解」** ❌ 这才是危险——出问题你都不知道在问什么

**所以这门课存在的意义，其实就是治第 7 条**：
你不用写代码，但你要**理解架构、能判断方案、能验收结果**。
资料里那句话说得更直接：

> 「**合格的技术管理者需要理解并指导系统架构**，Agent 使用者的技术基本功很重要。」

**这一条值得单独强调**——因为它证明你想过「用什么态度用 AI」，
而不只是会调 API。

### 为什么这七条值得记住

**「多 Agent 有什么坑」这个问题，答案分四层**：
- 只答「成本高」→ 入门
- 能说出「**错误级联**和**同质趋同**」→ 说明真设计过
- 能说出「**第 6 条过早终止**」并补一句「**循环的瓶颈在验证器，不在模型**」→ **工程视角**
- 能补上「**第 7 条是人的问题，技术解决不了**」→ **这是有洞察的答案**

## 4.5 单 Agent 的三个补丁：规划 / 记忆 / 反思

即使不拆多 Agent，复杂的单 Agent 也需要三个机制撑着。这三个是行业公认的 Agent 核心能力，也是最容易考的三块。

### 补丁一：任务规划（Planning）

**问题**：一个任务有 10 步，Agent 走一步看一步，容易迷路。

**解法**：先让它**列出计划**，再逐步执行。

| 方式 | 做法 | 适合 |
|---|---|---|
| **先规划后执行**（Plan-and-Solve） | 一次性列出所有步骤，再一步步做 | 步骤明确、不太会变的任务 |
| **边做边规划**（ReAct，阶段 3 学过） | 每步看结果再决定下一步 | 情况会变、需要纠偏的任务 |
| **先粗后细**（计划可调整） | 先列大步骤，做的时候允许改 | 最贴近实际工程的折中 |

**关键要点**：能说清「规划是为了防止长任务里迷路，但计划太死就失去了纠偏能力」，比背名词有价值。

#### ⭐ 进阶一点：光给「步骤上限」不够，要给「预算意识」

资料里讲了一个**反直觉的研究结论**（**「步骤预算与 Agent 性能」**）：
> 「**单纯增加 Agent 可用的步骤数并不能保证性能提升。**
> 标准的 Agent 缺乏「预算意识」——即使有 300 步的预算，它们仍然倾向于**执行浅层搜索，很快就「饱和」了**。」

**翻译成人话**：给它更多步数，**它不会用得更聪明**，它会**做一阵就停在那儿了**。

**所以关键不是「允许它走多少步」，而是让它「知道还剩多少步」**——
**前期广泛探索，后期聚焦最有希望的方向**（这叫**预算感知机制**）。

**这条对多 Agent 的直接启示**：
管理者 Agent **不该只是把任务分发下去然后等结果**，而应该**按任务复杂度动态分配步骤预算**——
**简单的子任务给少、复杂的给足**，并且**引导子 Agent 先规划再干**，而不是一头扎进去就写。

> **一句话**：**给预算不够，还要给「还剩多少预算」的感觉。**

### 补丁二：记忆机制（Memory）

**问题**：阶段 0 讲过，模型没有记忆，上下文窗口一满就忘最早的事。

**解法**：给 Agent 配一套「记忆系统」。

**⭐ 这里要先把术语对齐**（**「记忆的层次结构」**）——
资料里的**「记忆层次」**（回答「**存在哪里**」）是这三层：

| 层 | 存什么 | 生命周期 | 实现手段 |
|---|---|---|---|
| **轨迹** | **当前这次会话**的完整事件序列（用户消息 + 模型回复 + 工具调用与结果） | 随会话 | 就是上下文窗口里的内容 |
| **用户长期记忆** | **跨会话**的事实、偏好 | 长期 | 存到文件/数据库，用的时候检索出来（**这就是 RAG**，阶段 2 讲过） |
| **业务状态** | **任务进行到哪一步** | 随任务 | 结构化存下来，任务可以中断再续 |

**关键认知**：**所谓「AI 有记忆」，本质都是「把内容存到外面，用到时再读回来」。**
模型本身永远没记忆——这句话阶段 0 就埋下了，这里收口。

> ⚠️ **一个最容易搞混的词：工作记忆**
> 「工作记忆」是**认知科学**里的说法，它对应的是 **Agent 的上下文窗口**——
> 是**用来处理当前任务的临时空间**，不是一个「存到文件里的东西」。
> **别把「工作记忆」和「业务状态」混为一谈**（前者是内存，后者是存档）。

#### ⭐ 重要：记忆有「三套分类体系」，它们是正交的

资料专门用一张表把这件事讲清楚——**因为记忆这个词太容易混，必须分层看**：

| 分类体系 | 回答的问题 | 具体类别 |
|---|---|---|
| **记忆层次** | **存在哪里？** | 轨迹 / 用户长期记忆 / 业务状态 |
| **存储格式** | 怎么存？ | 简单笔记 / JSON 卡片 / 结构化对象等（表达力越强、维护越贵） |
| **认知类型** | 存什么？ | **情景**记忆（具体事件）／**语义**记忆（一般知识）／**程序**记忆（做事流程） |

**三套可以自由组合**：比如「用户偏爱靠窗座位」是一条**语义记忆**，
用**简单笔记格式**存在**用户长期记忆**里。

**能说出「记忆要分三个维度看——存哪里、怎么存、存什么」，
就比只会说「短期/长期」高一个层次**，因为那说明你知道**这不是一个单维问题**。

> **和阶段 2 的接口**：阶段 2 讲的**用户记忆 vs 知识库**，对应到这张表里就是
> 「用户长期记忆」这一层里的两种内容。**别把两者当同一个东西。**

### 补丁三：自我反思（Reflection / 自我修正）

**问题**：模型不知道自己错了（阶段 0 的第三条边界）。

**解法**：让它在给出答案后，**自己检查一遍**，或者**让另一个 Agent 检查**。

常见的两种：

| 方式 | 做法 |
|---|---|
| **自我批评**（Self-Refine） | 出答案 → 让它自己找问题 → 根据反馈改 |
| **外部评审** | 出答案 → 交给独立的评审 Agent/规则 → 返修 |

**为什么「检查」这一步可能有效**：模型「生成」和「检查」用的大脑状态不一样。
让它换个角度重看自己的输出，**有机会**发现问题。

**代价**：多一轮甚至多轮调用，成本上升。

#### 🔴 但「自己查自己」经常是无效的——这里有个反直觉的研究结论

资料里引了一篇 ICLR 2024 的研究（**「提议者-审核者范式」**）：

> 让 GPT-4 **在没有外部反馈的情况下**审查并修正自己的回答，**准确率反而下降**——
> **模型把正确答案改错的次数，比把错误答案改对的次数更多。**

**为什么会这样**：因为「自己查自己」**没有引入任何新信息**——
它只是在**同一个模型、同一份材料**里又想了想。
这正好回到 4.1 的**第一判断标准**：**没有信息增量的协作，是无效的。**

#### ⭐ 有效反思的两条硬条件（这是本节最该带走的）

资料给了「提议者—审核者」循环的**最小不变量**，两条：

**① 审核者必须读「独立证据」，而不是只复述提议者的解释。**
> 「审核者读取**独立证据**，而不是只复述提议者的解释」

**什么叫独立证据**：**测试结果、渲染出来的截图、真实的文件状态、外部工具查到的事实**——
**是「跑出来的东西」，不是「它说的东西」**。

这条直接解释了 4.4 第 6 条**过早终止**该怎么治：
**「做完了」不能听它说，要看测试跑没跑、跑过没有。**

**② 审核者不能自己改「验收标准」。**
> 「**审核者不能修改测试、证据采集器或发布门槛；否则「独立验证」会退化成自我批准。**」

**为什么这条关键**：如果审核者**既能判、又能改规则**，那它想让什么通过就能让什么通过——
**这就不叫验证了，叫自己给自己盖章。**

**换个大白话的类比**：
> 审核者相当于**质检员**。质检员可以判定「这批货不合格」，
> **但不能自己把合格线往下调**——那样他永远能判合格。

#### ⭐ 为什么这两条值得单独记住

**这两条不是抽象理论，本身就是一套可执行的验收协议。**

一套能用的验收协议长这样：
**不读每一行代码，但设计让它失败的场景，
并要求 AI 汇报时单独列出「没验的」「验不了的」**——
**这套办法，正好满足上面这两条**：
- 「设计会失败的场景」= **要独立证据**（不是听它说，是让它跑给你看）
- 「单独列出没验的」= **防止审核者自己降低标准**（防假全绿）

谈「怎么验收 AI 的产出」时，把这两条说出来，就有理论支撑了。

> 🧩 **自测点**（这题最容易暴露理解漏洞）：如果让同一个模型「自己审自己写的代码」，
> 你觉得能审出问题吗？为什么？——**能审出的很有限**：它没有拿到新信息（没跑测试、没看截图），
> 属于「同一份材料再想一遍」。**这正是 4.1 第一判断标准的反例。**

## 4.6 一个完整的例子：把「写一份行业报告」拆开

| 阶段 | 谁做 | 做什么 | 输出 |
|---|---|---|---|
| 1 | 主管 Agent | 拆任务：要哪些章节、每章要点 | 结构化任务清单 |
| 2 | 检索 Agent（可并行多个） | 每章去查资料 | 每章的素材（带出处） |
| 3 | 撰写 Agent | 按素材写初稿 | 初稿 |
| 4 | 评审 Agent | 挑事实错误、逻辑断裂 | 问题清单 |
| 5 | 撰写 Agent | 按问题清单返修 | 终稿 |
| 6 | 主管 Agent | 汇总、统一格式 | 输出 |

**注意两点**：
- 第 2 步可以并行，这是多 Agent 省时间的地方
- 第 4、5 步是「反思」循环，可能要来回几轮，**必须设上限**

## 4.7 章节小测：能答上来才算真会了

> 合上讲义自测。每题答得出来才算真会；答不出来的，回对应小节重读。

| 自测题 | 常见误解 | 正确理解 |
|---|---|---|
| 什么是多 Agent？ | 「就是很多个 AI 一起干活」 | 说**拆解逻辑**：把一个大循环拆成几个小而专的循环 |
| **什么时候不该用多 Agent？** | 「Agent 越多越强」 | ⭐ **第一判断标准**：协作有没有引入单 Agent 拿不到的新信息？没有就别拆——多出来的是几倍到十几倍的成本 |
| 多 Agent 有什么坑？ | 「成本高」 | ⭐ 说**七种失败模式**，重点讲**错误级联**、**同质趋同**、**过早终止**；再加一句第 7 条是「人的问题」 |
| 多 Agent 怎么通信？ | 「它们自己聊」 | ⭐ **先说两层平面**（数据平面放产物 / 控制平面管调度），再说**三种机制**：工具参数 / 共享文件 / 消息总线；消息要带**信封** |
| Agent 之间怎么交换大文件？ | 「发过去」 | ⭐ **传路径，不传内容**——虚拟文件系统四类区域（专属工作区 / 共享空间 / 外部挂载 / 系统内置），**共享空间才是并发冲突的高发地** |
| **Agent 怎么记住之前的事？** | 「它有记忆功能」 | 说**记忆层次三层**：轨迹 / 用户长期记忆 / 业务状态；再加一句**记忆有三个维度**（存哪里 / 怎么存 / 存什么）。注意**「工作记忆」= 上下文窗口**，别和业务状态混。**并区分用户记忆和知识库**（阶段 2） |
| Agent 做错了怎么办？ | 「让它重做」 | 说**反思机制**，并且**给出两条硬条件**：审核者读**独立证据**（不是复述解释）、**不能自己改验收标准**。补一句「同模型互审不算独立证据」 |
| Agent 说自己做完了，你怎么知道它是真做完了？ | 「看它报告」 | ⭐ 说**过早终止**：**「完成」只是一句宣称，不是证明**；**瓶颈在验证器不在模型**——要拿执行结果/截图/工具验证这类**独立证据**来判 |
| 长任务 Agent 会迷路怎么办？ | 「把提示词写详细」 | 说**规划**：先列计划再执行；或边做边规划（ReAct）。**进阶**：光给步骤上限不够，要让它有**预算意识**（前期广探、后期聚焦） |
| 多 Agent 一定更可靠吗？ | 「人多力量大」 | ⚠️ 说**容错性确实更好**，但**Agent 的故障是拜占庭式的**——它**不停机，给看似可信的错结论**。所以「多个 Agent」本身不带来可靠，**带来可靠的是独立验证** |

---

## 本阶段要带走的四句话

1. **多 Agent 是拆解，不是升级。** ⭐ **第一判断标准：协作有没有引入单 Agent 拿不到的新信息？**
    没有就别拆——多出来的是几倍到十几倍的 token 成本。
    **再加一条前置认知：Agent 的故障是拜占庭式的**——它不停机，给看似可信的错结论。
2. **不共享上下文的协作 = 数据平面 + 控制平面。**
    数据平面管「**东西放哪**」（虚拟文件系统四类区域，**共享空间是冲突高发地**，大产物**传路径不传内容**）；
    控制平面管「**谁在干什么、要不要停、给多少钱**」（消息传递 / 状态查询 / 执行终止 / 资源调度）。
    两种维度看架构：上下文共享还是独立 × 对等/管理者/去中心化。
3. **七种失败模式**：并发冲突 / 错误级联 / 同质趋同 / 互相扯皮 / 循环失控 /
    **过早终止**（「完成」只是宣称，不是证明；**瓶颈在验证器不在模型**）/
    **理解债与认知投降**（最后这条是人的问题，技术解决不了）。
4. **复杂 Agent 靠三个补丁撑着**：规划防迷路（**要给预算意识，不只是步骤上限**）、
   记忆防遗忘（**轨迹 / 用户长期记忆 / 业务状态，三套维度正交**）、
   反思防不自知（**审核者要读独立证据，且不能自己改验收标准**）。
